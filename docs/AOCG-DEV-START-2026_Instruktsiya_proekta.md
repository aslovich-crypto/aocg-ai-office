## 01а. Обязательный принцип работы — «Лучшая практика прежде всего»

**Перед тем как предложить любое решение — думать, искать и предлагать лучшее.**

Это означает:

1. **Изучить как делают лучшие** — анализировать хорошие российские и мировые аналоги (Тинькофф, Сбер, PILX, Revolut, Ramp, Linear, Stripe и другие). Не придумывать с нуля то, что уже хорошо решено.

2. **Обосновывать выбор** — объяснять почему предлагается именно это решение, а не альтернативы. Если есть несколько вариантов — честно сравнивать.

3. **Учитывать российскую специфику** — законодательство РФ (152-ФЗ, ФЗ-402, НК РФ), популярные в России сервисы (Яндекс, Mail.ru, ФНС, DaData), платёжные системы, хостинг в России.

4. **Не молчать о лучшем** — если есть более правильный подход который не был запрошен явно, предложить его. Например: если пользователь просит форму логина с email — предложить OAuth кнопки как лучшую практику, а не просто делать форму.

5. **Стоимость имеет значение** — всегда искать бесплатные или дешёвые решения если они не уступают платным. Не предлагать платные сервисы без явной причины.

6. **Называть конкурентов и референсы** — указывать конкретные приложения и сервисы как пример правильного решения. Это помогает принять решение.

**Примеры правильного поведения:**
- Просят форму логина → предложить OAuth (Google, Яндекс, Mail.ru) + email как запасной вариант
- Просят SMS-верификацию → объяснить что SMS платный, предложить бесплатные альтернативы
- Просят React компонент → сначала проверить есть ли готовая библиотека (Lucide, Recharts и тд)
- Просят хранить файлы → предложить S3-совместимое хранилище с учётом 152-ФЗ

**Примеры неправильного поведения:**
- Предложить SMSC.ru (платный SMS) не упомянув что SMS вообще не нужен
- Сделать форму логина только с email не предложив OAuth
- Не упомянуть конкурентов при обсуждении функционала

## 10. Авторизация — экран логина

Лучшая практика (как у PILX, Контур, Битрикс24):

```
[G Google]  [Я Яндекс]  [@ Mail.ru]

────────── или ──────────

Телефон или Email
Пароль [👁]
[Войти]
```

**OAuth в приоритете:** один клик, email подтверждён провайдером, пользователь не создаёт ещё один пароль.
**Email + пароль:** запасной вариант.
**Провайдеры:** Яндекс ID (основной для РФ), Google (универсальный), Mail.ru (популярен в РФ).

## 13а. Методология работы — обязательные практики

Эти практики выработаны на сессиях 22-26 мая 2026 и подтверждены реальной пользой (десятки предотвращённых багов и ошибок). Применять во всех будущих задачах.

### 13а.1. Принцип «one feature, one session»

Не запускать вторую задачу пока первая не закоммичена и не задеплоена. Каждая сессия = одна закрытая фича. При исключениях (когда задача делится на пакеты) — обязательно проговаривать стратегию заранее.

### 13а.2. Регламент аудита перед каждой большой задачей

**Перед каждой задачей из очереди** — сначала промпт-аудит Claude Code, который фиксирует текущее состояние кода/БД. Только потом — рабочие промпты.

Без аудита промпты строятся на устаревшей картине → баги и переделки. На сессии 23-26 мая регламент сработал **8+ раз**, каждый раз предотвратив реальную проблему.

**Три шаблона аудита:**

**Шаблон А — Аудит перед изменением СХЕМЫ БД**
Используется перед: расширение схемы, Альфа-Банк, ФНС Мои чеки, любые миграции.
Запрашивает: точные схемы таблиц через information_schema, индексы, эндпоинты, формат POST/GET, тесты, прод-маркеры, HEAD коммиты обоих репо.

### 13а.4. BEGIN/ROLLBACK валидация миграций БД

**Обязательно перед любой миграцией схемы БД на проде.**

Прогоняем новый DDL внутри транзакции BEGIN/ROLLBACK — синтаксис проверяется реальным движком PostgreSQL, но ничего не сохраняется.

**Почему:** `init_db()` выполняется в FastAPI lifespan на каждом старте контейнера приложения. Синтаксическая ошибка в DDL = приложение не поднимется = прод лежит. Валидация ловит это заранее без риска.

**Как:**
```python
# через asyncpg (psql локально не стоит — Алексей не разработчик)
# ⚠️ ПОПРАВКА 27.08 (T65): `railway run` больше не существует. Строка
# подключения берётся из панели Timeweb ВНЕШНИМ адресом базы:
#   DATABASE_PUBLIC_URL=postgresql://... ./venv/bin/python validate.py
# Точная команда запуска с бастиона НЕ ЗАМЕРЕНА — проверить ДО миграции.

tr = conn.transaction()
await tr.start()
await conn.execute(NEW_DDL)          # синтаксис
await conn.execute(NEW_DDL)          # идемпотентность (вторая прогонка = no-op)
# проверка схемы через information_schema.columns / pg_indexes
await tr.rollback()                  # finally — НИКОГДА не COMMIT
# контрольный SELECT после отката: схема не изменилась
```

Применять для **всех будущих миграций**: №5 Альфа-Банк, №6 ФНС, №7 D/E, №13 user_consents и т.д.

### 13а.14. Контрактные тесты `keys_match` для параллельных парсеров (открыт 26.05.2026)

**Когда несколько парсеров пишут в одни и те же колонки БД через общий INSERT** — обязательно добавлять тест что **множество ключей** возвращаемого dict одинаково между ними.

**Применимо к:**
- `parse_fns_response` (qr_scan / fns источник)
- `parse_ocr_response` (photo_ocr источник)
- **Будущие парсеры**: `parse_alfabank_response` (задача №5), `parse_fns_lkdr_response` (задача №6)

**Без контрактного теста:** один парсер пропустит ключ, INSERT запишет NULL молча, баг будет необнаружим в проде.

**Пример теста:**
```python
def test_keys_match_fns():
    sample_fns = {...}
    sample_ocr = {...}
    fns_result = parse_fns_response(sample_fns)
    ocr_result = parse_ocr_response(sample_ocr)
    assert set(fns_result.keys()) == set(ocr_result.keys()), \
        f"Parsers diverge: fns={set(fns_result.keys()) - set(ocr_result.keys())}, " \
        f"ocr={set(ocr_result.keys()) - set(fns_result.keys())}"
```

**Регулярная проверка:** при добавлении нового поля в `parse_fns_response` — этот тест немедленно покажет что `parse_ocr_response` ему не зеркален. Защита от молчаливой поломки прода.

### 13а.15. Нормы РФ — закладывать проактивно, не реактивно (открыт 30.06.2026)

При любой задаче с фискальными данными, налогами, ПД, документооборотом — **СНАЧАЛА свериться с действующей нормой РФ** (стандарт ФФД/тег, статья НК, ФЗ) и заложить **ПОЛНЫЙ набор значений по норме**, а не только то, что встретилось в текущих данных пользователя. ### 13а.16. Пауза перед кодом — её держит владелец, а не агент (открыт 06.09.2026)

Правило «аудит перед задачей» (13а.2) описывает **что** делать. Эта глава описывает, **кто стоит между чтением и кодом**, — и это владелец.

**Промпт двухчастный, но остановка — по условию, а не всегда.**
Агент останавливается после замера, если:

- **замер вскрыл развилку** — два и более варианта с разной ценой, и выбирать
  между ними не по технике, а по тому, как работает бюро;
- **правка трогает схему базы, гейты доступа, деньги** (суммы, статусы
  отчётов, НДС) **либо юридические тексты**;
- **замер опроверг постановку** — предпосылка неверна, и задача в записанном
  виде не делается.

Во всех остальных случаях агент пишет **«замер подтвердил постановку,
продолжаю»** — и продолжает без остановки.

```
ЧАСТЬ 1 — ЧТЕНИЕ. Код не править.
⚠️ Сработало одно из трёх условий — ОСТАНОВИТЬСЯ, показать выкладку,
   ждать «ок». Не сработало — «замер подтвердил постановку, продолжаю».
ЧАСТЬ 2.
```

**Приёмка после правки остаётся за владельцем ВСЕГДА** — витрина, снимок
с телефона, живая проба. Ослаблена пауза ПЕРЕД кодом, а не проверка ПОСЛЕ
него; это разные вещи, и вторая не двигается.

**⚠️ УЛИКА, РАДИ КОТОРОЙ ПРАВИЛО ОСЛАБЛЕНО (решение владельца 09.09.2026).**
За 04–09.09.2026 пауза окупилась восемь раз и столько же раз была
формальной. **08.09 — три случая подряд в один день:** замер по [[T172]]
(геометрия строки списка), по [[S-79]] (заголовки писем), по обязательности
имени и фамилии. Все три ПОДТВЕРДИЛИ постановку, все три получили «ок»
без чтения. **Пауза стоила обмена сообщениями и не поймала ничего.**
Правило, срабатывающее вхолостую в половине случаев, обесценивает себя
и в той половине, где оно нужно: «ок» начинают давать не глядя.

**⚠️ ГРАНИЦА ОСЛАБЛЕНИЯ, И ОНА НЕ ПЕРЕГОВОРНАЯ: на три условия выше
ослабление НЕ распространяется — там пауза ЛОВИЛА, и вот чем.**

| где | что поймала пауза |
|---|---|
| [[T166]] | развилка: запрещать удаление или пересчитывать — выбор не технический |
| [[UX-19]] / [[UX-20]] | формат подписи автора — решение дизайн-линии, не кода |
| обязательность фамилии | спрашивать при приглашении или при первом входе — вопрос про то, как работает бюро |

Общее у трёх: **ни один не решается замером.** Замер там отвечал на «как
устроено», а решать надо было «как должно быть» — и это не вопрос к агенту.

**⚠️ ПРИЗНАК ГРАНИЦЫ, ОДНОЙ ФРАЗОЙ И ПРОВЕРЯЕМЫЙ: если ответ можно получить
замером — паузы не нужно; если нельзя — нужна.** Три условия выше — это три
формы одного и того же: развилка по тому, как работает бюро, схема и деньги
и право, опровергнутая предпосылка — всё это вопросы «как должно быть», на
которые прибор не отвечает по устройству. Проверка перед кодом простая:
спросить себя, что именно я жду от владельца — число или решение. Число
добывается без него.

**Между частями — когда остановка сработала — агент показывает не только находки, но и что изменится:** какие файлы и строки, что станет по-другому на экране, какие решения остаются за владельцем. «Ок» должно даваться со знанием, а не на доверии.

**«Ок» даёт владелец своим словом** — там, где остановка сработала. Готовая формулировка из чата — это заготовка; если владелец с чем-то не согласен, это должно всплыть до кода, а не после. **Там, где остановки нет, несогласие всплывает на приёмке — и это принятая цена ослабления 09.09.2026, а не недосмотр.**

**⚠️ Признак сползания, проверяется механически:** если промпт содержит и чтение, и правку без остановки перед владельцем **при сработавшем условии выше** — правило уже нарушено, независимо от того, насколько мелкой кажется задача. Проверять признак, а не намерение: намерение всегда доброе.

**Почему это не формальность.** За 04–06.09.2026 приборы врали трижды: двойник базы давал 32 зелёных теста на сломанном коде; сторож мерил соседний экран, где механизм был, — при том что на нужном его не было вовсе; замер читал собственный исходник и находил в нём искомое. **Каждый раз ловил человек** — владелец глазами на телефоне или агент, споткнувшийся по дороге. Ни разу не поймал прибор. Пауза перед кодом — одно из двух мест в процессе, где смотрит человек; второе — приёмка после правки. **С 09.09.2026 там, где паузы нет, всю нагрузку несёт приёмка** — поэтому её и нельзя двигать.

### 13а.17. Размер захода и борьба с хвостами (открыт 06.09.2026)

**Задача закрыта, когда есть всё пять:** код · сторож по нужному экрану · мутации, каждая покраснела · приёмка владельца на проде · строка в трекере. Четыре из пяти — это не «почти закрыто», а открытая задача.

**Находка по ходу — ЧЕРНОВАЯ СТРОКА В ТРЕКЕРЕ, и заводит её АГЕНТ** (правило 06.09.2026). Признак черновика — `✏️ ЧЕРНОВИК · ` в начале ячейки «Задача» плюс статус ⏸. **В очередь и в блок «▶ ПОРЯДОК ВЫПОЛНЕНИЯ» черновик не берётся, пока владелец его не утвердил** — иначе агент назначает работу себе сам. Утверждение — словом владельца: агент тем же коммитом снимает префикс и ставит ⬜. **Одна находка — одна строка:** находка того же класса, что УЖЕ ОТКРЫТАЯ строка, идёт пунктом в неё, а не новой строкой. Не заводится вовсе то, что чинится этим же заходом, — это часть работы, а не находка.

**Дополнение «не вклиниваться посреди работы» ОСТАЁТСЯ.** Черновики заводятся молча и перечисляются в КОНЦЕ отчёта одним списком; предлагать завести строку в середине задачи нельзя — это сбивает работу сильнее, чем стоит сама строка.

**ПОЧЕМУ ПРАВИЛО ПОМЕНЯЛИ — чтобы через месяц было понятно, от чего лечились.** Прежнее правило 03.09.2026 звучало так: «находка по ходу — фразой в отчёте, строку заводит владелец». Его вводили в день, когда закрыли 8 строк и завели 14: очередь росла быстрее, чем таяла, и заведение строк агентом эту гонку разгоняло. Правило работало, но 06.09.2026 находки ТРИЖДЫ едва не потерялись — фраза в отчёте живёт до конца переписки и дальше не живёт, — а напоминания о них посреди работы сбивали. Заведение вернули агенту, но рост очереди сдерживает теперь не запрет заводить, а то, что **черновик не участвует в очереди до просмотра**. Порог: больше пяти черновиков означает, что владелец давно не просматривал (прибора нет, записано пунктом ⑦ T178). ⚠️ Граница этого числа: считались ВСЕ заведённые строки, а не находки агента — таких данных нет вовсе, правило работает с 06.09.2026. Перемерить через неделю работы по новому правилу.

**Правило одного класса.** Заход чинит **один класс, но во всех местах** — не одно место и не пять разных проблем. «Пустой catch по всему фронту» — один заход. «Пустой catch и заодно подпись автора» — два.

**Порог дробления.** Заход, где больше ~10 мест правки или больше ~2 часов, делится. Довод не в усталости, а в разборе: один коммит на 15 мест, если поедет на проде, разбирается в куче.

**⚠️ УКРУПНЕНИЕ ЗАХОДА — ОБРАТНЫЙ ХОД К ПОРОГУ, И ОН РАЗРЕШЁН С 09.09.2026
НА УСЛОВИЯХ.** Владелец даёт больше двух часов, если аудит впереди захода и
мутации остаются. Две РАЗНЫЕ строки делаются одной сессией, не сводясь
в одну строку, когда сходятся все три: ① один репозиторий; ② правки не
пересекаются по файлам либо пересекаются в одном файле и не спорят;
③ у каждой строки свои мутации, и мутация одной не роняет проверки другой.
**Не укрупняются никогда:** правки схемы базы (по одной, с валидацией
владельца), гейты доступа (по одной, с мутацией на каждый), строки с решением
владельца внутри — они останавливаются, и вторая строка ждёт.

**⚠️ ГЛАВНОЕ ИЗ ПЕРВОГО АУДИТА НА УКРУПНЕНИЕ (09.09.2026), И ЭТО ПРАВИЛО,
А НЕ ОГОВОРКА: ЗАХОД ОБЪЕДИНЯЕТ СТРОКИ ТОЛЬКО ТАМ, ГДЕ ЕСТЬ ЧЕМ ПРОВЕРИТЬ
РЕЗУЛЬТАТ ЦЕЛИКОМ.** Улика: шесть открытых строк (T57, T87, T112, T151,
T156, T194) делят один файл — `docs/RULES-FRONTEND.md` — и по критериям
① и ② сходятся идеально; группа не предложена. У документа нет мутаций,
критерий ③ невыполним в принципе, и такой заход нечем проверить, кроме
чтения — а «прибор не запускался» мы зовём дефектом, а не проверкой.
**Отсюда: документы, правила и наблюдения не укрупняются.** Их единственная
проверка — чтение, и укрупнение сделало бы её ещё дальше от предмета.

**Граница самого критерия ②:** он проверяется только у строк, которые
называют свои файлы. Замер 09.09.2026 — из 157 строк живой работы файлы
названы у 62; остальные 95 в укрупнении не участвуют не потому, что не
подходят, а потому, что про них нечего проверить. Строка без адреса
планируется вслепую (находка записана владельцем отдельной строкой).

**Не расширять объём по ходу.** Нашёл смежный дефект — фразой в отчёт. Единственное исключение: правка в **том же файле** и **того же класса**, иначе заход перестаёт быть одной задачей и его нельзя ни принять, ни откатить целиком.

**⚠️ Правило распространяется и на разговор, а не только на заход агента.** Побочный вопрос владельца — не повод бросать текущую задачу. Ассистент отвечает «это отдельная строка, вернёмся» и возвращает разговор к тому, что делается сейчас. Переключение возможно, но только явным решением владельца, а не потому, что новое показалось интереснее ассистенту.

**Улика 08.09.2026:** задача T172 получила решение владельца и не была начата. От вопроса про формат подписи разговор ушёл к копиям формата, оттуда к семи местам сборки имени, оттуда к обязательности полей и миграции схемы, оттуда к трекеру и пересборке блока порядка. Ни один шаг не был запланирован — каждый вырос из предыдущего. Владелец заметил это через несколько часов.

**И повторно в тот же день:** после закрытия T39 ассистент предложил взять T41, всплывшую в её отчёте, — при том что владелец уже отправил промпт по T172. Отчёт закрытой задачи — обычный источник таких соблазнов: он честно называет находки, и каждая выглядит уместной именно сейчас.

**Признак сползания:** ассистент собирает промпт по вопросу, который не относится к задаче в работе. Проверяется механически — как и признак из 13а.16. Находка из отчёта идёт в конец сообщения списком «на завести», а не промптом.

**Хвост называется явно.** Закрывая задачу, агент перечисляет, что осталось, отдельными пунктами с оценкой. Формулировка «осталось по мелочи» запрещена: она и есть способ, которым хвосты становятся невидимыми.

### 13а.18. Периодический аудит очереди на объединение (открыт 06.09.2026)

**Когда:** при накоплении 5+ открытых строк в одном домене, либо раз в неделю, смотря что раньше.

**Три вопроса к паре строк:**

1. Один ли это класс — то есть чинится ли одним приёмом?
2. Один ли экран или файл?
3. Один ли прибор их проверит?

**Два «да» из трёх — объединять.** Одно «да» — оставить порознь: объединение ради экономии переключений, а не ради общего слова в заголовке.

**⚠️ ЧАЩЕ ВСЕГО СВОДЯТ ПО ОБЩЕМУ СЛОВУ В ЗАГОЛОВКЕ, А НЕ ПО ОБЩЕМУ ПРИЁМУ.** 06.09.2026 три пары подряд проверены этими тремя вопросами, и ни одна не выдержала: T22+T39 (слово «дубли»), T181+T183 (слово «защита»), T107+T109 (слово «кабинет» — ноль «да» из трёх: разные приёмы, разные места, разные приборы). Общее слово в заголовке — признак того, что пару стоит ПРОВЕРИТЬ, а не того, что она одна работа.

**⚠️ УЛИКА В ПОЛЬЗУ ПРАВИЛА, ПРОВЕРЕННАЯ ВРЕМЕНЕМ, А НЕ РАССУЖДЕНИЕМ: ПАРА
T84 И T86.** 28.08.2026 их хотели свести — обе про одного сторожа трекера,
обе заведены в один день, у обеих в заголовке слово «не видит». Владелец
настоял завести порознь с доводом: **T84 про то, что прибор не смотрит нужную
ТАБЛИЦУ, T86 — про то, что он не узнаёт нужный ФОРМАТ; починки разные.**

**06.09.2026 одна из пары закрылась, вторая нет.** T86 сняла работа по T188
(разбор научился голой цифре — проверено прибором форм), а T84 осталась жива
дословно: порог `len(я) < 8` в `tracker_guard.py` на месте, таблица очереди
из четырёх столбцов по-прежнему невидима.

**Что было бы при сведении:** половина работы спряталась бы ВНУТРИ закрытой
строки. Строка стояла бы ✅, потому что «сделано то, ради чего заводили», —
и невидимость очереди всплыла бы через месяц, как REP-CRUD. **Это довод не за
осторожность вообще, а за конкретное правило: два „да“ из трёх, и первое из
них — „чинится ли одним приёмом“.** Здесь ответ был «нет», и через девять дней
это подтвердилось фактом.

**Обратный ход тоже нужен.** Строка, описывающая пять мест разом, дробится, если места чинятся разными приёмами: такая строка выглядит как одна задача, а стоит как пять, и оценка по ней всегда врёт.

**Отделять вопросы от работ.** Строка, где решение владельца ещё не принято, — это вопрос, а не задача; в оценке очереди она не участвует и в план сессии не берётся. Помечать явно: «ждёт решения владельца».

**⚠️ Перед постановкой задачи из очереди — сначала замер, жив ли дефект.** Особенно для строк старше недели. Примечание строки писалось в момент заведения, до того как причину нашли, и после этого не перечитывалось — а работа могла быть снята соседней задачей.

**Улика, ради которой правило введено:** 06.09.2026 три блокера подряд закрылись замером и ни один не потребовал кода. T103 — три пункта из четырёх сняли T104 и T168, четвёртый снял запрос к проду (беспарольных строк ноль). T125 «белый экран» — причина была починена 31.08, в день заведения строки, но примечание осталось в состоянии «причина не найдена». T169 — сделана заходом B соседней задачи. Все три неделю числились работой, будучи сделанными.

**Цена ошибки несимметрична:** замер стоит десять минут, постановка мёртвой задачи — целый заход и место в порядке. Поэтому замер делается всегда, а не когда есть сомнение.

**⚠️ ГДЕ ИСКАТЬ МЁРТВЫЕ СТРОКИ: ЗАВИСИТ ОТ ТОГО, ИЗ ЧЕГО СТРОКА РОДИЛАСЬ.**
Замер 06.09.2026, заход B аудита: блок «Безопасность» — **32 открытые строки,
мёртвых НОЛЬ**. Причина не в аккуратности, а в происхождении: почти каждая
строка там заведена по ЗАМЕРУ ПРОДА С УЛИКОЙ — событие Sentry, журнал доступа,
запись DNS, ответ сервера.

**Строка, рождённая из замера, не умирает молча: у неё есть, что перепроверить.**
Улику можно снять заново — и она либо подтвердится, либо опровергнет саму строку
(так S-35 закрылась как «предмета нет», а S-47, S-50 и S-52 — замерами владельца
в тот же день). **Строка, рождённая из плана или из мысли, устаревает вместе с
обстоятельствами и об этом молчит:** перепроверять в ней нечего, потому что
исходного факта не было.

**Улики обратного — все восемь мёртвых строк, найденных 06.09.2026:** T22, T103,
T107, T116, T125, T169, T36, REP-CRUD. Все из блоков, где работа шла быстро:
приглашения, кабинет, отчёты, тесты. Там строку писали как план на завтра, а
завтра приходило раньше, чем до неё доходила очередь.

**СЛЕДСТВИЕ ДЛЯ ПОРЯДКА АУДИТА: начинать с блоков, где строки заводились ПЛАНОМ,
а не замером.** Блок с уликами проверяется быстро и почти ничего не даёт; блок
с планами даёт мёртвые строки пачками. Признак происхождения виден по первым
словам примечания: «ЗАМЕР …», «УЛИКА …», «событие …» — против «нужно сделать»,
«добавить», «предусмотреть».

**⚠️ ТРЕТИЙ СОРТ, И ОН ХУЖЕ МЁРТВОЙ СТРОКИ: ПРОТУХШАЯ ПРЕДПОСЫЛКА.**
Строка жива, работа осмысленна, но её ПЕРВОЕ ПРЕДЛОЖЕНИЕ описывает систему,
которой больше нет. Мёртвая строка просто занимает место — эта **выглядит
исполнимой и упирается в середине работы**, когда заход уже начат и время
потрачено.

**Улики 06.09.2026, отчётная часть блока «Продукт»:** REP-SPLIT опирается на
«способ оплаты уже на уровне чека (личная/корпоративная/наличные)» — трёх
классов не существует, `receipts.payment` свободный текст из имён карт, а
признака «личная/корпоративная» у карты нет вовсе. REP-UNAPPROVE (пункт ③) и
REP-ONBEHALF обе ждут журнала аудита S-08, не начатого за месяц.

**ПРОВЕРЯТЬ ОТДЕЛЬНЫМ ВОПРОСОМ, А НЕ ВМЕСТЕ С ОСТАЛЬНЫМИ: верно ли первое
предложение примечания СЕГОДНЯ?** Вопрос не «сделана ли работа», а
**«существует ли то, на что строка опирается»**. Это разные проверки: первая
смотрит на результат, вторая — на исходные данные, и вторая обычно не делается
вовсе, потому что предпосылка выглядит частью постановки, а не утверждением о
мире.

**Строка с протухшей предпосылкой не закрывается и не переписывается молча** —
она уходит в ⏸ с записью, ЧЕГО не существует и какая работа должна встать
перед ней. Иначе следующий заход начнётся с того же места и остановится там же.

**⚠️ УТОЧНЕНИЕ К ПРИЗНАКУ ПРОИСХОЖДЕНИЯ, ЗАМЕР 06.09.2026 (заход по блоку
«Продукт»). Признак отвечает на вопрос «протухнет ли предпосылка», а НЕ «узнает
ли строка о своём закрытии».** Второе зависит не от происхождения, а от того,
**шла ли работа рядом**, — и строка с уликой рискует ровно так же. Улики:
T125 (починена в день заведения, примечание осталось «причина не найдена») и
строка 19 «В своде Итого нет НДС» — обе рождены ЗАМЕРОМ, обе закрыты работой
соседних задач, обе пролежали открытыми неделями.

**⚠️ И ПОПРАВКА К СЛЕДСТВИЮ, ЗАПИСАННОМУ ПОСЛЕ ЗАХОДА ПО БЕЗОПАСНОСТИ.**
Плановые строки не умирают, **пока за них не брались**: замер 06.09 по блоку
«Продукт» дал по ним нули грепом — работа просто не начиналась, поэтому и
устареть было нечему. Умирают те, **за которые брались**. Значит аудит очереди
начинать не с «плановых» блоков, а **с тех, ГДЕ ШЛА РАБОТА за последний месяц**:
там строка и закрывается попутно, и не узнаёт об этом.

**⚠️ ЧЕТВЁРТЫЙ СОРТ: ПРЕДПОСЫЛКА ЕЩЁ НЕ НАСТУПИЛА.** Отличие от третьего
(протухшей) в том, что там предпосылка устарела, а тут её **не было никогда**.
Строка выглядит независимой работой и упирается в отсутствие данных.

**Улика 06.09.2026:** строка 18 «Показ фото чека» (миниатюра, просмотр, зум,

переносит расхождение на следующее сообщение.

исходе:** контроль был выбран так, что отрицательный результат опроверг бы

правило выводится из наблюдений, а не из устройства системы.

**Как ставить такой контроль:** взять случай, который по правилу обязан вести
себя определённым образом, и проверить его ПЕРВЫМ, до всех остальных — пока
результат ещё нельзя подогнать под ожидание. Проверять правило на случаях,
из которых оно и выведено, смысла нет.

**ЛЕЧИТСЯ ДВУМЯ СПОСОБАМИ СРАЗУ, И ИМЕННО СРАЗУ:**

1. **Прибор ОБЯЗАН печатать, чего он не взял — даже при нуле.** «Отброшено 0

2. **Второе число берётся ДРУГИМ ходом, не через ту же функцию.** Сырой счёт,

слепа к потерям до фильтра; сырой счёт слеп к тому, что фильтр выбросил
осознанно. Вместе они меряют РАЗНОЕ — в этом и смысл.

`Cat-H`, `TAX`, `UX`, `R-QR`, `R-UNIT`), в прежних заходах аудита все девять
получили вердикт «жива» или «предмета нет» — то есть НЕ сделана ни одна. Ни
одного расхождения. **Это самостоятельный вердикт: быстрый фильтр «точно не
сделана», строку читать не обязательно.** Он работает потому, что отвечает
отрицанием: сделанной работы без единого следа в коде не бывает.

**НЕНАДЁЖНАЯ ПОЛОВИНА — «первый коммит по предмету раньше заведения строки»:
совпало 3 из 10, семь ложных, 70 %.** Расхождения: `NDS-ЧП5`, `R-BRAND`,
`R-ITEMS`, `R-SHIFT`, `REP-ONBEHALF`, `SCAN-UI`, `UX-5`. **Это НЕ вердикт, а
повод открыть строку и посмотреть глазами.**

**Почему ложных так много: вопросы разные.** `git log -S` отвечает «когда слово
впервые появилось в коде», а строка спрашивает «когда предмет сделан». Улика —
`UX-5`: слово `#C45558` впервые попадает в `875550d` «first commit», то есть в
день заведения репозитория; признак объявляет работу давно сделанной, а на деле
цвет просто лежал в палитре с первого дня. Слово живёт в коде задолго до того,
как появляется поведение, ради которого строку завели.

**ВТОРАЯ ГРАНИЦА: `git log -S` НЕ ВИДИТ ТЕМЫ КОММИТОВ.** Именно `Cat-A2` — та
улика, ради которой наблюдение и записано, — признаком поймана вердиктом, но не
основанием: «fix A2» стоит в ТЕМЕ коммита `834176b`, куда `-S` не смотрит, а по
слову `org_brand` первым выпадает `debb83e` «add 20 columns» — это схема, а не
логика приоритета бренда. Вердикт совпал по случайности. **Поиск обязан идти
двумя ходами: `git log -S` по содержимому И `git log --grep` по темам.** Совпали
оба — можно доверять; разошлись — читать код глазами.

**ТРЕТЬЯ ГРАНИЦА, РЕКОРД ДНЯ: РАБОТА МОЖЕТ ИДТИ ПАРАЛЛЕЛЬНО ЗАВЕДЕНИЮ.** `UX-21`
(«у формы „Добавить чек“ нет макета») заведена 06.08.2026 в **23:29:27**
(`b8bb9d1`), а коммит, закрывающий её первый вопрос — формат суммы в этой самой
форме, — сделан 06.08.2026 в **23:45:54** (`39c4589`). **Шестнадцать минут.**
Строка не родилась мёртвой и не умерла позже: работа шла В ТОЙ ЖЕ СЕССИИ, что
и заведение — сначала записали вопрос, следом на него ответили, а строку
не поправили.

**Признак такой случай не поймает НИКОГДА, и это устройство, а не промах:**
коммит здесь ПОЗЖЕ заведения, то есть по признаку строка выглядит безупречно
живой. Ловится он только чтением — или сторожем, которого нет.

**Вывод для аудита: свежесть строки не довод в её пользу.** Строку, заведённую
в день активной работы по её же домену, читать глазами независимо от дат.
«Завели вчера, значит актуальна» — та же ошибка, что «завели давно, значит
протухла», только с другим знаком.

**ЧЕТВЁРТАЯ ГРАНИЦА — ГДЕ ИСКАТЬ: только по коду** (`app/`, `tests/`, `src/`,
`scripts/`), `docs/` исключать всегда. Первая редакция этого замера искала по
всему репозиторию и принимала за работу собственные записи в трекер; разбор
случая — в девятом наблюдении выше, случай ③.

**ПРАКТИЧЕСКИЙ ВЫВОД: при переносе или массовом заведении строк сверять с кодом
КАЖДУЮ.** Дороже, чем завести списком, — но дешевле, чем держать
несуществующий долг в очереди и оценивать его в часах. При аудите порядок такой:
сперва надёжная половина сплошным прогоном (она снимает вопрос по части строк
одним ходом), затем ненадёжная — как список кандидатов на чтение, не как ответ.

**⚠️ ОДИННАДЦАТОЕ: ПРЕДМЕТ СТРОКИ МОЖЕТ ЛЕЖАТЬ ТАМ, КУДА СЕССИЯ НЕ ДОСТАЁТ.**
Не «иногда попадается», а **свойство устройства работы**: за один день
06.09.2026 таких строк набралось ПЯТЬ мест, и это уже не исключение.

1. **Макеты** `design/handoff/` — под `.gitignore`, копия единственная,
   истории нет, возраст поставки измерить нечем (UX-4, UX-19, UX-20, UX-21,
   UX-26; правило — в `docs/RULES-FRONTEND.md`).
2. **Google Apps Script владельца**, вызывающий наш шлюз, — кода нет ни
   в одном репозитории (S-71, T54, T187).
3. **Скрипты оснастки на сервере** — `08-dump-restore.sh`, `09-verify.sh`,
   `lib-snapshot.sql`: git не знает их ни в одном репозитории (T48, T49).
4. **Переменные площадки** — `POSTBOX_FROM` правится в панели Timeweb,
   в коде лежит только имя переменной (T68, T69).
5. **Данные и настройки внешнего сервиса** — `chat_id` группового чата MAX
   жил в чужом скрипте, и минус в нём терялся при копировании (T58, частично).

**ЧТО ДЕЛАТЬ С ТАКОЙ СТРОКОЙ ПРИ АУДИТЕ: подтверждать ТОЛЬКО ТЕКСТ и говорить
это прямо.** Живость предмета проверяет владелец там, где предмет лежит.
Опасность ровно в обратном: прочитать строку, не найти противоречий и записать
«жива» — это выдаёт чтение за проверку и ничем не отличается от неё в отчёте.

**ПРИЗНАК СТАВИТЬ В САМОЙ СТРОКЕ**, чтобы следующий заход не тратил на неё
время дважды и не решил, будто предмет проверен.

**И СЛЕДСТВИЕ ДЛЯ ПЛАНИРОВАНИЯ, НЕ ТОЛЬКО ДЛЯ АУДИТА:** такая строка не может
быть закрыта сессией в одиночку — в её оценке всегда есть шаг владельца.
Считать её «работой на 30 минут» неверно: тридцать минут там наши, а решает
дело чужой замер.

**⚠️ ДВЕНАДЦАТОЕ: ЗЕЛЁНЫЙ СТОРОЖ ОТВЕЧАЕТ ПРО СВОЙ СТЫК, А НЕ ПРО ПРЕДМЕТ.**
Подтверждено ДВАЖДЫ на разных предметах — 08.09.2026 на налоговых словарях и
в тот же день на ролях. Опыт один и тот же: в источнике на бэке появляется
новое значение, порождённая копия НЕ пересобирается. После этого сторож во
фронте **зелёный, и честно зелёный**: штамп копии сходится с её же
содержимым, экран знает ровно то, что в копии. Красной становится только
python-половина (`gen_dictionaries.py --check`) — она одна читает код бэкенда.

**Два прибора на один предмет стерегут РАЗНЫЕ СТЫКИ:** JS — «копия ↔ экран»,
python — «код ↔ копия». **Ни один не заменяет другого, и зелёный одного не
говорит про второй ничего.** Отсюда правило чтения отчётов: «сторож зелёный»
— неполный ответ, пока не названо, КАКОЙ СТЫК он стережёт. **Родня по классу — «зелёный
сторож не равен доехавшей правке»** (замер 10.08.2026: сторож был зелён, а до
человека правка не доехала). Там зелёный не означал доставки, здесь — не
означает сошедшегося источника; общее в том, что зелёный цвет отвечает про
ОТРЕЗОК, а его принимают за ответ про всю цепь.

**⚠️ ТРИНАДЦАТОЕ: ДУБЛЬ ВНУТРИ ОДНОГО ИСТОЧНИКА. Канон бывает объявлен дважды
в ОДНОМ файле, и тогда «единственный источник» — иллюзия.** Найдено 08.09.2026
на ролях: `app/auth.py` объявляет их кортежем `ROLES` (по нему валидируются
формы, заводящие человека) и `Literal` в типе `Role` (по нему pydantic
отвергает запрос). Разойдись они — половина входов принимает роль, которую
вторая половина не признаёт, и молча. **До сверки этого не ловило ничто: файл
один, глаз ищет дубли между файлами, а объявлений в нём два.** Лечение —
сверка внутри генерации: расхождение останавливает порождение копий и
называет обе стороны поимённо.

**ЗАМЕР КЛАССА ПО ВСЕМ ЧЕТЫРЁМ НАБОРАМ ПРОЕКТА, В ТОТ ЖЕ ДЕНЬ:**

| набор | объявлений в файле-источнике | сходится сегодня |
|---|---|---|
| роли (`auth.py`) | **2** — кортеж `ROLES` и `Literal Role` | да |
| статусы отчёта (`reports.py`) | **4** — `Literal StatusIn` плюс два ПОДМНОЖЕСТВА (`EDITABLE_STATUSES`, `APPROVAL_STATUSES`) и умолчание `'Черновик'` в SQL (`database.py`) | да |
| источники чека (`receipts.py`) | **3** — кортеж `SOURCES`, `DEFAULT_SOURCE`, перечисление в комментарии типа | да |
| режимы организации, коды ФНС | **1** | — |

**У СТАТУСОВ КЛАСС ПРИНИМАЕТ ХУДШУЮ ФОРМУ, И ЕЁ СТОИТ НАЗВАТЬ ОТДЕЛЬНО: ЭТО
НЕ РАВНЫЕ СПИСКИ, А ПОДМНОЖЕСТВА.** Совпадать они не обязаны — обязано другое:
каждый элемент подмножества **входит** в канон, и умолчание в SQL тоже.
Сверка «списки равны» тут не годится, нужна сверка «⊆». Цена промаха
несимметрична и тиха: опечатка в `EDITABLE_STATUSES` («Отклонен» без ё) не
ломает ничего заметного — отчёт просто перестаёт быть редактируемым, а
`Literal` эту опечатку не видит, потому что она не в нём.

**ПРИЗНАК КЛАССА, ПО КОТОРОМУ ЕГО ИСКАТЬ:** в одном файле рядом с каноном
лежит второй набор тех же значений — кортеж, подмножество, значение по
умолчанию, перечисление в комментарии или в строке SQL. Все они обязаны
проверяться ПРОТИВ канона, а не глазом.

**⚠️ ЧЕТЫРНАДЦАТОЕ: ЗАМЕР, ПОВТОРЁННЫЙ В ТРЕТИЙ РАЗ, ОБЯЗАН СТАТЬ ПРИБОРОМ.
Это не про аккуратность, а про то, что одноразовый замер НЕ НАКАПЛИВАЕТСЯ.**
Улика 08.09.2026, и она про способ работы, а не про правило: сверку «блок
порядка ↔ факт трекера» агент написал ЗАНОВО ТРИЖДЫ ЗА ТРИ ЗАХОДА — при
пересборке блока, при закрытии одной строки и при закрытии следующей. Каждый
раз это был скрипт в оболочке на десять строк, каждый раз он давал верный
ответ, и каждый раз его выбрасывали вместе с выводом команды. **Прибор
существовал по десять минут и ни разу не сохранился.**

**ЭТО КЛАСС «СДЕЛАЛИ И НЕ ПОДКЛЮЧИЛИ», ДОВЕДЁННЫЙ ДО ПРЕДЕЛА: здесь даже
не сохранили.** Разница с обычным случаем того класса важна. Написанное и
неподключённое хотя бы ЛЕЖИТ в репозитории: его найдёт следующий заход,
поймает сторож достижимости, увидит человек в диффе. Написанное в оболочке
не оставляет следа вовсе — ни в git, ни в поиске, ни в чужой памяти. Третий
такой замер выглядит как первый, и стоит столько же.

**ПРИЗНАК, ПО КОТОРОМУ ЛОВИТЬ СЕБЯ:** рука тянется написать замер, который
УЖЕ писали. Не «похожий» — тот же. Один раз это разведка, два — совпадение,
**на третьем разе замер обязан переехать в файл под именем**, даже если
кажется, что больше не понадобится: он уже понадобился трижды.

**⚠️ ВТОРАЯ ПОЛОВИНА УЛИКИ, И ОНА НЕОЧЕВИДНА: ОТСУТСТВИЕ ПРИБОРА СТОИТ
НЕ ТОЛЬКО ПРОПУЩЕННЫХ НАРУШЕНИЙ, НО И ЛОЖНЫХ ТРЕВОГ.** В тот же день
владелец потребовал зачеркнуть пункт блока, который БЫЛ УЖЕ ЗАЧЁРКНУТ:
он смотрел на витрину, собранную до нужного коммита. Ошибка стоила захода
и была ровно того же происхождения, что нарушение правила часом раньше —
**состояние, которое никто не сверяет прибором, приходится держать
в голове, а голова ошибается в обе стороны.** Поэтому прибор нужен не для
того, чтобы ловить нерадивость: он нужен, чтобы ни у кого — ни у агента,
ни у владельца — не было надобности помнить.

**ЧЕМ ЭТО КОНЧИЛОСЬ:** сверка переехала в `tests/tools/tracker_html_guard.py`
одной функцией — обе половины сравнения там уже лежали, — и получила три
парные мутации. Цена постройки оказалась меньше, чем трижды написать
её заново.

**⚠️ ПЯТНАДЦАТОЕ: СПЛОШНАЯ ПРАВКА КЛАССА ИЩЕТ ФОРМЫ, А НЕ ОДНУ ЗАПИСЬ.
Перечень форм составляется ЗАМЕРОМ, а не догадкой.** Улика 10.09.2026:
задача T171 «отказ сервера превращается в пустоту» была закрыта сплошной
правкой по ШЕСТИ источникам — и через два дня аудит соседней задачи нашёл
СЕДЬМОЙ, живой и того же класса. Опись источников составлялась поиском
по `.catch(() => {})`; в найденном месте отказ проглатывался **другой
формой** — ранним `return` по `!res.ok`. Один класс, две записи в коде;
поиск знал одну.

**ЧЕМ ЭТО ОТЛИЧАЕТСЯ ОТ ДЕВЯТОГО НАБЛЮДЕНИЯ, и путать их не надо.** Там
область поиска была ШИРЕ предмета и находила лишнее. Здесь она УЖЕ
предмета и не находит нужного — при этом отчёт выглядит полным: шесть
из шести, все правлены, прибор зелёный. **Ложный зелёный от неполной
описи неотличим от настоящего.**

**ПОЧЕМУ ЭТО НЕ ЛЕЧИТСЯ ВНИМАТЕЛЬНОСТЬЮ.** Класс живёт в СМЫСЛЕ («отказ
не доехал до человека»), а поиск работает по ЗАПИСИ («вот такие символы»).
Между смыслом и записью всегда больше одного соответствия, и первая
найденная форма кажется единственной именно потому, что она нашлась.

**КАК ДЕЛАТЬ, ПО ПОРЯДКУ:**

1. **Назвать класс словами, без синтаксиса.** Не «`.catch(() => {})`»,
   а «отказ сервера не доходит до человека».
2. **Выписать формы, которыми это может быть записано** — и выписать
   ЗАМЕРОМ: искать по СЛЕДСТВИЮ, а не по образцу. Для отказов это
   `catch`, ранний `return`, `?? []`, `|| {}`, проглоченный `await`,
   пустой обработчик события.
3. **Прогнать опись по каждой форме отдельно** и сложить числа: «шесть
   мест формы А, один формы Б» — а не «семь мест».
4. **Записать перечень форм в саму строку.** Следующий заход по этому
   классу начнётся с него, а не с нуля.
5. **Мутация ставится на КАЖДУЮ форму**, не на класс целиком: мутант
   одной формы не краснеет на приборе, знающем другую.

**ПРИЗНАК, ПО КОТОРОМУ ЛОВИТЬ СЕБЯ:** опись класса собрана ОДНИМ
поисковым запросом. Один запрос — одна форма; классов из одной формы
почти не бывает.

**Что проверять при аудите очереди, кроме объединения:**

- строки, закрытые наполовину (код есть, приёмки нет) — они хуже открытых, потому что выглядят готовыми;
- строки старше месяца без движения — либо в работу, либо снять с доводом;
- дубли по смыслу под разными ID — сводить, оставляя историю обеих.

### 13а.19. Снятие ветки двойника может повысить права соседней (открыт 06.09.2026)

**Правило:** прежде чем снять ветку FakePool, прогнать сторож зеркал
(`tests/tools/mirror_gaps.py`). Ветки разбираются по порядку, первое совпадение
выигрывает — значит **порядок веток общий ресурс**, и удаление специфичной ветки
передаёт её запрос более общей, у которой условий меньше.

**«Никто не звал» и «снимать безопасно» — разные утверждения.** Первое доказуемо
трассировкой: прогнать сюиту под `sys.settrace` и посмотреть, исполнялось ли тело
ветки. Второе трассировкой НЕ доказуемо вовсе: снятая ветка меняет поведение
соседней, а соседняя может обслуживать запрос, которого в этом прогоне не было.

**Улика, ради которой правило введено.** 06.09.2026, T36 заход 4: из 124 веток
трассировка нашла 43 пустых, сняли 40 — и сторож зеркал покраснел на двух.
`DELETE FROM receipts … AND user_id=$3` после снятия перехватывала общая ветка
удаления и теряла `user_id`; `UPDATE users SET is_active = false … AND org_id=$2`
уходила в общую `UPDATE users SET` и теряла `org_id`. То есть **снятие мёртвого
кода ослабило проверку живого** — при том, что каждая снимаемая ветка была
доказанно пустой. Обе возвращены и помечены по месту.

**Порядок действий при снятии:**

1. трассировка обеих сюит — тело ветки не исполняется ни на одном контуре;
2. сверка предмета: обслуживаемый веткой запрос либо исполняется живым контуром
   (предмет переехал), либо в приложении такого запроса больше нет вовсе;
3. снятие;
4. **`mirror_gaps` — обязательно**, и он же решает, что вернуть;
5. повторная трассировка: ни одна из исполнявшихся веток не должна перестать
   исполняться, ни одна не должна начать перехватывать чужое.

**Пустая ветка, которую нельзя снять, помечается по месту** — комментарием с
доводом, иначе следующий заход снимет её заново. Отдельно помечать случай
«ветка пуста, потому что путь не проверяется НИ ОДНИМ контуром»: это находка о
непокрытом коде, а не мусор в двойнике.

Связано: 13а.8 (зеркальная правка conftest при смене продакшен-логики).

### 13а.20. Решение «про одну кнопку» против решения «про картину» (открыт 06.09.2026)

**Заведено по слову владельца 03.09.2026, дословно:** «я вчера согласился
на Ⓑ, ты его предложил, и оба были неправы — потому что решали про одну
кнопку, а не про картину. Разбор целиком отменил решение, принятое по частям».

**Случай, на котором записано.** Лупа на «Сводке» прошла ТРИ решения за два
дня: заглушка ради единообразия полос (то есть обман жеста) → переброс
в поиск «Главной» (навигация, переодетая поиском; приняли оба) → разбор всех
шести мест поиска в приложении: на «Сводке» нет ПРЕДМЕТА поиска, там агрегаты,
и лупа снята вовсе. **Каждое частное решение выглядело разумным; неверность
видна только из целого.**

**Правило: повторяющийся элемент не решается на одном экране.** Поиск, полосы,
подписи роли, свайп-действия, пустые состояния — это КАРТИНА, и решение по ней
принимается после обзора всех мест, где элемент живёт. Обзор дешевле отката:
здесь он стоил двух решений и одной правки, которую пришлось снимать.

**Как отличить, что перед тобой картина, а не кнопка:** элемент встречается
больше чем на одном экране — значит картина. Если встречается один раз,
но по смыслу обязан быть и на соседних, — тоже картина.

**⚠️ Рамку ставить ДО перебора вариантов.** Шесть предложенных реализаций
не заменяют вопроса «а этот элемент здесь вообще нужен» — родня правила
о дизайн-линии в `docs/RULES-FRONTEND.md`.

Улики и счёт случаев — строка T155 в трекере.

### 13а.21. Состояние не живёт в документе (открыт 07.09.2026)

**Правило: если запись описывает СОСТОЯНИЕ — схему базы, список переменных,
перечень файлов, — ей не место в документе, который правят руками.** Она
живёт там, где её можно получить командой, или там, где её сверяет прибор.
Правила устаревать не могут, состояние устаревает всегда.

**Куплено разбором четырёх глав Инструкции 07.09.2026 (T176).** Три из
четырёх оказались состоянием, и каждая протухла молча:

- **гл. 08 «База данных»** — снимок схемы. В главе 9 таблиц, в коде 15;
  колонок `receipts` в главе 13, в коде 41, и одна из тринадцати не
  существует вовсе. **Глава сама первой строкой говорила «не полагаться на
  статичный список» — и держала его сорок строк.** Читали список.
- **гл. 09 «Переменные окружения»** — реестр имён. Из 28 совпало с кодом
  **10**; 18 мертвы, 22 действующие не описаны. При этом у переменных УЖЕ
  было два источника, и один под прибором (`env_check`, S-49). Глава была
  третьей копией и самой старой.
- **гл. 16 «Приоритеты»** — снимок очереди на 21.05.2026. Честно помечен
  историческим, и всё же лежал рядом с действующими правилами.
- **гл. 15 «Реестр документов»** — пограничная: перечень устарел (16 файлов
  репозитория в нём не значились), а правило «код всегда с понятным
  названием» не устарело ни на день. **Такую главу не снимают целиком:
  снимают состояние, оставляют правило.**

**⚠️ ПОЧЕМУ «ПЕРЕПИСАТЬ ЗАНОВО» — ХУДШИЙ ИЗ ВЫХОДОВ.** Он даёт верный
документ ровно на один день и возвращает задачу через месяц. Дороже
переписывания только одно: переписать и поверить, что теперь не протухнет.

**ЧТО ДЕЛАТЬ ВМЕСТО ЭТОГО, ПО УБЫВАНИЮ ПРЕДПОЧТЕНИЯ:**
1. **снять запись, оставив способ получить состояние** — команда, путь
   к файлу с DDL, ссылка на опись;
2. **отдать состояние прибору**, который сверяет его сам и говорит при
   расхождении (образец — `env_check` в журнал деплоя);
3. **переписать руками** — только когда первых двух нет и предмет меняется
   реже, чем раз в квартал.

**⚠️ И ОТДЕЛЬНО, ЧТОБЫ СПИСОК НЕ ВПИСАЛИ ОБРАТНО: снимая состояние, надо
записать НА ЕГО МЕСТЕ, почему его больше нет и чем оно кончилось.** Иначе
следующий читатель увидит пустоту, сочтёт её пропуском и заполнит. В главах
08 и 09 такие абзацы стоят с числами замера — это не самооправдание, а
предохранитель.

### 13б.1. Защита учётных данных и секретов

**Никогда не коммитить секреты в репозиторий:**
- API-ключи, токены, пароли, JWT-секреты → только в панель Timeweb → Переменные
- `.env` файлы → в `.gitignore`
- Перед каждым `git push` мысленно проверять что в diff нет ключей

**Если секрет случайно попал в коммит:**
- НЕ просто удалить файл в новом коммите — секрет остаётся в git history
- Сразу ротировать ключ у провайдера (Anthropic, proverkacheka, Альфа-Банк и т.д.)
- При публичном репо — использовать `git filter-repo` или BFG для очистки истории
- Записать инцидент в техдолг для аудита

**Хранение секретов в панели площадки:**
- Все секреты с префиксом сервиса (`ANTHROPIC_API_KEY`, `JWT_SECRET_KEY`, ...)
- Никогда не дублировать секрет между сервисами — каждый сервис имеет свои
- Для смены провайдера (R2 → Yandex Object Storage) — только меняем значения, код не трогаем

**Минимизация прав:**
- API-токены — с минимально необходимыми scope (например, Анthropic API только messages.create, не admin)
- DaData бесплатный план — только nominatim запросы, не записи
- Альфа-Банк — read-only где возможно

### 13б.2. Аутентификация и сессии

**JWT — текущая реализация:**
- Access токен — 60 минут (ACCESS_TOKEN_EXPIRE_MINUTES)
- Refresh токен — 30 дней (REFRESH_TOKEN_EXPIRE_DAYS)
- HMAC-SHA256 (HS256) с 64-символным секретом
- При logout — токен добавляется в `revoked_tokens` (нельзя просто «забыть» — пользователь может его сохранить локально)

**Защита от перебора паролей:**
- 5 неверных попыток → блокировка 15 минут (`failed_attempts` + `locked_until` в users)
- Реализовано в `app/auth.py` — не убирать при рефакторинге

**Хеширование паролей:**
- Только bcrypt (стоимость 12+)
- Никогда не хранить пароли в открытом виде
- При логировании — никогда не выводить `password` поле даже в debug-логах

**OAuth — приоритетный путь (когда будет внедрён):**
- Один клик — лучше чем форма логина
- Email верифицирован провайдером (Яндекс/Google/Mail.ru)
- Пользователь не создаёт ещё один пароль (меньше уязвимостей)

**Восстановление пароля:**
- Только через email с одноразовой ссылкой (срок жизни 15 минут)
- Никогда не присылать новый пароль в открытом тексте
- После сброса — invalidate всех существующих сессий пользователя

### 13б.4. Защита от инъекций

**SQL Injection:**
- Только параметризованные запросы asyncpg (`$1`, `$2`, ...)
- НИКОГДА не строить SQL через f-strings или конкатенацию
- Проверять каждый новый запрос — нет ли `f"SELECT ... {user_input}"`

**XSS (Cross-Site Scripting):**
- React автоматически экранирует `{переменная}` — это базовая защита
- НИКОГДА не использовать `dangerouslySetInnerHTML` без явной санитизации
- Если приходит HTML от пользователя (например, в названии организации) — экранировать на бэке

**Injection в логи (log injection):**
- Пользовательский ввод в логах может содержать `\n` и спуфить другие записи
- При логировании произвольных строк — экранировать или ограничивать длину

### 13б.5. Защита от ботов и DDoS

**Rate limiting:**
- slowapi (FastAPI) — на критичных эндпоинтах
- POST `/api/receipts/` — 60 запросов/мин на пользователя
- POST `/api/auth/login` — 5 запросов/мин на IP (защита от перебора)
- POST `/api/fns/check` — 30 запросов/мин (защита от исчерпания лимитов proverkacheka)

**Cloudflare Turnstile:**
- Бесплатная защита от ботов от Cloudflare (альтернатива reCAPTCHA)
- На формах регистрации и логина
- Невидимая для пользователя в 95% случаев

**Защита от автоматизированных атак:**
- Email верификация при регистрации — нельзя зарегистрировать на чужой email
- При подозрительной активности (10+ неверных логинов с одного IP за минуту) — IP-блок на 1 час

### 13б.6. CORS и заголовки безопасности

**CORS:**
- Только whitelist домены в `CORS_ORIGINS`
- Сейчас: `https://app.aocgai.ru`  ⚠️ ПОПРАВКА 27.08

**Security Headers (обязательные на проде):**

Площадка даёт HTTPS; остальные заголовки — в FastAPI middleware

### 13б.7. Защита файловых загрузок

**Валидация типов:**
- Проверка по MIME-type **и** по расширению **и** по магическим байтам (header)
- accept в HTML — только подсказка, не защита
- На бэке — всегда проверять заново

**Размер:**
- `MAX_UPLOAD_SIZE_MB=5` для фото чеков
- Возвращать 413 (Payload Too Large) для превышений

**Хранение:**
- Файлы — в S3-совместимое хранилище, не в БД
- Имена файлов — генерировать (UUID), не использовать пользовательские
- Доступ — через signed URLs с TTL, не публично

**Сканирование:**
- Изображения от пользователей — проверять не содержат ли EXIF с координатами (приватность)
- При R2/Yandex Object Storage — настроить чтобы EXIF удалялся при загрузке

### 13б.8. Защита от утечек через ошибки

**Production режим:**
- `ENVIRONMENT=production` → отключить traceback в ответах API
- 500 ошибки — возвращать общее сообщение «Внутренняя ошибка сервера»
- Полный traceback — только в server logs

**Защита от энумерации:**
- При логине неверный email и неверный пароль — одинаковая ошибка «Неверный логин или пароль»
- Никогда не «Пользователь не найден» (это позволяет узнать какие email зарегистрированы)
- При восстановлении пароля — всегда «Если email зарегистрирован, ссылка отправлена»

**Стек-трейсы в Sentry/логах:**
- При интеграции Sentry — фильтровать чувствительные поля из трейсов
- `password`, `password_hash`, `card_number`, `cvv`, `inn`, `fn` — никогда в трейсе

### 13б.9. Безопасность зависимостей

**Обновление пакетов:**
- Раз в квартал — `pip list --outdated` + `npm outdated`
- Особое внимание — пакеты с CVE
- Использовать `pip-audit` и `npm audit` периодически

**Минимизация зависимостей:**
- Перед добавлением нового пакета — проверить размер и зависимости
- Не добавлять «just in case» — каждая зависимость = поверхность атаки

**Pinned versions:**
- В `requirements.txt` — фиксированные версии (`==`)
- В `package.json` — fixed versions, не `^` или `~`
- Это защищает от supply chain атак через обновления

- Реализовать запрос «как есть» без замечаний о безопасности
- Использовать deprecated алгоритм (например, MD5 для хешей) без предупреждения
- Не упомянуть про rate limiting на критичных эндпоинтах

### 13б.12. Checklist перед каждым деплоем

Перед `git push` на main для критичных задач (затрагивающих auth, БД, файлы, API ключи) — мысленно или явно проверять:

```
☐ Нет секретов в diff?
☐ Все новые пользовательские входы валидируются?
☐ Все SQL-запросы параметризованы?
☐ Нет логирования чувствительных данных?
☐ CORS не открыт для `*`?
☐ Новые эндпоинты требуют авторизации (где нужно)?
☐ Rate limiting на критичных эндпоинтах?
```

## 14. UX-принципы подсказок и помощи в приложении

Сквозное правило для всех будущих UI-задач. Сформулировано на сессии 28.05.2026 после обсуждения системы помощи по категориям. Применять ко всем подсказкам, tooltips, onboarding и контекстной справке в приложении.

### 14.1. Принцип «подсказка = приглашение, не лекция»

Подсказка должна появляться **по запросу пользователя**, а не **навязываться ему**. Хорошие приложения (Linear, Stripe, Figma, Notion) соблюдают этот принцип неукоснительно.

**Что отличает зрелое приложение от плохого:** уважение к вниманию пользователя. Навязчивые подсказки убивают UX больше, чем помогают.

### 14.2. Три уровня подсказок

**Уровень 1 — Контекстные иконки `?` (всегда видны, молчат до тапа)**

Маленькие нейтральные иконки `?` или `ⓘ` рядом со спорными полями или элементами. Появляются как часть UI и **не делают ничего** пока пользователь сам не тапнет.

- Цвет — нейтральный серый, не привлекает внимания
- Размер — небольшой, не доминирует
- **НЕ отключаемые** — не мешают, всегда под рукой, как `?` в macOS
- При тапе — короткий tooltip или ссылка на полную справку

**Пример:** иконка `?` рядом с пилюлей категории в форме чека → тап → «Категория = как трата учтётся в налогах. Не уверены? Поставьте "Не учитываемые в НУ"».

**Уровень 2 — Янтарные подсказки при реальной проблеме**

Появляются **только** когда система обнаруживает потенциальную проблему (например, фолбэк «Прочие хозрасходы» при категоризации).

- Мягкий янтарный цвет, без мигания и движения
- Не пищат, не блокируют действие
- Если пользователь не реагирует — спокойно остаются на месте
- **Отключаемые** в Настройках — опытным пользователям не нужны

**Пример:** «Проверьте категорию» при автоматической установке фолбэка.

**Уровень 3 — Onboarding-туры при первом действии**

Короткие обучающие подсказки появляются **только при первом** использовании функции.

- 2-3 шага максимум
- В каждом шаге — кнопка «Не показывать снова»
- После прохождения — **исчезают навсегда**
- Можно **вернуть** в Настройках (для нового сотрудника)
- Состояние «пройдено» хранится в `users.onboarding_*` или localStorage

**Пример:** при первом добавлении чека — 3 экрана о категориях.

### 14.3. Глобальное управление в Настройках

Все отключаемые подсказки и обучение собираются в одном разделе:

```
Настройки → Уведомления и подсказки

☑ Подсказки о категориях
☑ Подсказки при сканировании
☐ Обучение пройдено · [Пройти заново]
```

Это даёт пользователю **полный контроль** над тем что он видит.

### 14.4. Чего НЕ делать

Запрещённые антипаттерны (встречаются в плохих приложениях):

- ❌ **Подсказки, всплывающие при каждом действии** — раздражают мгновенно
- ❌ **Бейджи «новое!» висящие месяцами** — теряют смысл, начинают мешать
- ❌ **Tooltips появляющиеся при наведении и не закрывающиеся**
- ❌ **Неотключаемые «обучающие» подсказки**
- ❌ **Onboarding без возможности пропустить**
- ❌ **Закрывающиеся уведомления возвращающиеся через сессию**

### 14.5. Хранение справки в репозитории

**Принцип:** markdown-файлы справки лежат **в коде проекта**, рядом с компонентами. Так делают Stripe, Linear, Figma.

```
~/aocg-ai-office-web/
└── src/
    └── help/
        ├── categories.md       ← готов (287 строк)
        ├── scanning.md          ← на будущее
        ├── reports.md           ← на будущее
        └── index.json           ← оглавление
```

**Преимущества:**
- ✅ Версионируется с кодом (git history, code review)
- ✅ Работает оффлайн (не требует внешнего CMS)
- ✅ Деплоится с приложением (всегда синхронно)
- ✅ Рендерится через `react-markdown` (стандартная библиотека)
- ✅ Бесплатно (никаких Intercom/Helpscout за деньги)
- ✅ Соответствует подходу Stripe/Linear

**Чего избегать:**
- ❌ PDF/файл для скачивания — пользователи не качают, забывают где сохранили
- ❌ Только внешний Notion/сайт — отрывает от приложения
- ❌ Большой статичный FAQ — не находится, не структурирован

### 14.6. План реализации — два этапа

**Этап 1 — Контекстные подсказки (быстро)**

Можно встроить в Фазу D2 или сделать отдельной маленькой задачей:

1. Иконка `?` рядом с пилюлей категории в форме чека → tooltip
2. Иконка `?` в шапке CategorySheet → tooltip с ссылкой на полную справку
3. Значок 🛡️ у статьи «Не учитываемые в НУ» с подписью «Безопасный выбор при сомнении»
4. Тоггл отключения янтарных подсказок в Настройках

**Этап 2 — Встроенный экран Помощи**

Отдельная задача после Этапа 1:

1. **Настройки → Помощь** — список разделов
2. Рендер markdown через `react-markdown` (импорт пакета)
3. Из tooltip'а Этапа 1 — переход на конкретную статью
4. Поиск по тексту (когда статей станет 5+)

### 14.7. Связь с другими принципами

UX-подсказки **дополняют**, но не заменяют:
- **Лучшая практика прежде всего** (01а) — анализ конкурентов до решения
- **Безопасность по умолчанию** (13б) — никаких чувствительных данных в подсказках
- **Сначала проговор UX, потом код** (13а.12) — обсудить расположение и текст до промпта
