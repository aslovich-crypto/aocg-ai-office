## Утверждённый UX-стандарт: алгоритм обработки файла чека

Это наш утверждённый UX-стандарт для **двух кнопок**: «Сделать фото» и «Загрузить» на экране сканирования чека. Обе используют **общий пайплайн** обработки файла — различаются только источником (нативная камера ОС vs медиатека/файл). При любых правках в этом потоке — сверяться с алгоритмом.

**Подтверждено аудитом 23.05.2026:** «Сделать фото» открывает нативную камеру ОС через `<input capture="environment">`, получает файл, затем идёт по тому же пайплайну что и «Загрузить» (pickFile → превью → usePhoto → QR-first каскад → ФНС или OCR).

**Также подтверждено:** камеру можно открыть **тремя способами** — все ведут в один и тот же `pickFile`, источник файла нигде не различается:
1. Кнопка «Сделать фото» → cameraInputRef (с `capture="environment"`)
2. Кнопка «Загрузить» → galleryInputRef → пользователь выбирает «Сделать снимок» в нативном меню
3. Кнопка «Загрузить» → galleryInputRef → пользователь выбирает «Медиатека» или «Выбрать файл»

После получения файла — байт-в-байт один и тот же код. Различается только что показывает iOS на третьем шаге (камера сразу vs меню выбора). EXIF не используется. Метаданные источника не сохраняются.

### Принципы

1. **Источник не важен** — медиатека, камера, файл, PDF — алгоритм один
2. **Тип файла прозрачен** — пользователь не видит разницы JPG/PNG/PDF
3. **QR-first** — всегда сначала фискальный QR (юр. сила максимальная)
4. **Multi-QR фильтр** — берём только настоящие ФНС, игнорируем чаевые/отзывы/рекламу
5. **Прозрачный прогресс** — каждый шаг с таймером
6. **Мягкий fallback** — при провале ФНС спрашиваем «сохранить как фото?»
7. **Финал всегда форма** — пользователь имеет последнее слово

### Архитектурные решения

1. **«Лучше лишний чек, чем потерянный»** — soft-warning не блокирует, пользователь решает сам
2. **in_report защита всегда** — блок не пробивается даже с force=true (бизнес-инвариант — отчёты должны быть консистентны)
3. **force пробивает только ФНС** — рекомендация не удалять юр.силу, но если пользователь явно хочет — можно
4. **Defense in depth** — UI отключает чекбоксы для ФНС/QR (🔒), бэк защищает через force=false по умолчанию
5. **Sticky без auto-dismiss** — баннер виден пока пользователь не закроет (не пропустит проблему)

### Известное ограничение дедупа

После ручного теста Алексей нашёл: при ручном вводе с разной датой дубль не обнаруживается; «Мере» vs «Ресторан Мере» с одинаковой датой обнаруживается (через слабый ключ date+amount).

**Архитектурное объяснение:**
- Дедуп **никогда** не сравнивает строки `org`
- Сильный ключ: date+amount+**org_inn** (числовой)
- Слабый ключ: date+amount (без org вообще)

**Решение:** Оставить как есть (Вариант D). Аргументы:
- Не критический баг
- Любое улучшение добавляет риск ложных срабатываний
- После задачи №6 (ФНС Мои чеки) ИНН будет везде → проблема исчезнет
- Философия «лучше лишний чек чем потерянный»

В техдолге: «дедуп не сравнивает строки org при ручном вводе без ИНН — осознанный архитектурный выбор, fuzzy match отложен».

### Фикс A2 — бренд-aware категоризация (`834176b`)

**Сигнатура:**

auto_categorize_v2(org_text: str, brand: str | None = None) -> str:

## Методологические принципы (накопленные)

1. **One feature, one session** — не запускать вторую задачу пока первая не закоммичена
2. **`git diff --cached --stat` перед каждым commit** — проверка staged файлов
3. **`pwd` перед каждым push** — критично для проектов с двумя репо
4. **Чекпойнты с явными паузами** для больших задач — ждать «ок» от человека
5. **`IS NOT DISTINCT FROM` для NULL-полей** в SQL
6. **При смене продакшен-логики править и `conftest.py`** — иначе тесты ложноположительны
7. **Деплой фронта Railway проверять через curl-маркеры по строковым литералам**, не через хэш бандла
8. **Аудит существующего кода перед промптом** — обязательно для архитектурных задач
9. **Defensive programming** в обработчиках развилок (например, `partial` как catch-all для HTTP)
10. **Стилизованные bottom-sheet вместо нативных confirm()** на мобиле
11. **Сначала проговор UX, потом код** — все архитектурные решения утверждать до промпта
12. **Аудит перед каждой большой задачей** — обязательная практика
13. **BEGIN/ROLLBACK валидация миграций БД на проде** — стандартная практика
14. **Контрактные тесты `keys_match`** — для параллельных парсеров одного INSERT-пути
15. **Гард-тесты от опечаток в коде** — пример: `test_v2_all_trigger_keys_are_real_categories` (Фикс №1 Фаза B)
16. **Обязательная сверка таблицы статистики перед любой оценкой времени** (открыт 29.05.2026) — алгоритм 5 шагов: открыть таблицу 13а.5 → найти аналог → применить его коэф → если аналога нет «новый тип, без коэфа до факта» → после факта пополнить таблицу. ## Уроки сессии 27.05.2026

1. **Регламент аудита — главная защита.** За день предотвращено 18 багов, которые без аудита попали бы в прод.

2. **Архитектурные решения требуют диагностики.** Задача №9 началась как 40-60 мин фикс, но после диагностики UX («баннер исчез, два дубля остались») превратилась в 4-фазную мини-фичу. Это правильно — мы делаем для пользователя, не для коммитов.

3. **Документация vs реальность.** При обсуждении Фикса №1 выяснилось что 24+ категорий со скриншота **никогда не существовали в коде**. Аудит спас от строительства на воздухе.

4. **Источник истины — 1С.** Когда стандарта нет (ФНС не классифицирует чеки), идём за лучшей практикой — структурой 1С Бухгалтерии. Это конкурентное преимущество: простой UI + правильная бухгалтерская структура.

5. **Гард-тесты от опечаток в коде.** `test_v2_all_trigger_keys_are_real_categories` — пример как тестом защититься от тихих ошибок в данных. Применимо везде где есть параллельные структуры данных в коде.

6. **«Лучше лишний чек, чем потерянный»** — правильный UX-принцип для финансовых документов. Применяется в дедупе (soft-warning + interactive resolution).

7. **Defense in depth** — UI ограничивает выбор пользователя (🔒 на ФНС-чеках), бэк проверяет ещё раз (force=false по умолчанию). Если UI взломан/сломан — данные защищены.

8. **tax_kind должен быть скрыт от обычного пользователя.** Это техническое поле для бухгалтера. ИП не должен видеть «Прочие расходы» / «Материальные расходы» — это пугает.
