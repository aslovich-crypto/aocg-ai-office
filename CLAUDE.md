## Что это за проект
Бэкенд платформы AOCG AI Офис — B2B SaaS для управления первичными финансовыми документами (чеки, авансовые отчёты, акты/УПД, счета) и управленческим учётом для российского малого и среднего бизнеса. Оператор персональных данных — ИП Шукалович Алексей Иванович.

## Технологический стек
- Язык: Python
- Фреймворк: FastAPI
- База данных: PostgreSQL через asyncpg (пул соединений)
- Хостинг: Railway (auto-deploy из main)
- CI: GitHub Actions, pytest на каждый push

## Команды
- Запуск локально: `uvicorn app.main:app --reload`
- Тесты: `pytest tests/ -v`
- Виртуальное окружение: `source venv/bin/activate`

## Структура репозитория и лимиты на размер
Куда класть новый код (раскладка обязательна, не импровизировать):
- Эндпоинты — в `app/routers/`, один файл = один домен (receipts, reports, categories...). Новый домен — новый файл роутера, не дописывать в чужой.
- Бизнес-логика (категоризация, парсеры, расчёты) — отдельными модулями (`app/categorization.py`, `app/parsers/`), НЕ внутри роутеров. Роутер только принимает запрос, зовёт логику, возвращает ответ.
- `app/main.py` — только сборка приложения (CORS, startup, подключение роутеров). Не складывать сюда бизнес-логику.
- Общие утилиты — `app/utils/` или отдельный модуль, не дублировать функцию между файлами.

Лимиты (это сигналы пересмотреть, не жёсткие запреты):
- Файл роутера > ~300 строк → сигнал, что в нём смешаны домены или логика просочилась из сервисного слоя. Предложить разделение.
- Функция/хендлер > ~50 строк → сигнал вынести часть в отдельную функцию.
- Дублирование одной логики в 2+ местах → вынести в общую функцию.
- При приближении к лимиту — не молчать, а сообщить и предложить, как разнести.

## Приложение «Финансы» — модуль «Бюджет проекта»
ТЗ: **AOCG-FIN-PBM-001 v0.1**. По терминологии выше: Финансы — это ПРИЛОЖЕНИЕ,
«Бюджет проекта» — МОДУЛЬ внутри Финансов (наравне с ДДС, ОПУ). Формулировка
«модуль Финансы» неверна, не использовать.

**Границы (жёстко).** Код Финансов живёт только здесь:
- бэкенд — пакет `app/finance/`;
- БД — таблицы с префиксом `fin_*`;
- фронтенд (репозиторий aocg-ai-office-web) — зона `src/finance/`.

Код и таблицы Примы (receipts, reports, report_items, receipt_items, categories,
category_groups, cards) НЕ трогать. Разрешённые касания вне пакета — ровно два,
оба минимальные:
- `app/main.py` — импорт роутера Финансов + `app.include_router(...)`;
- `app/database.py` — один вызов `init_finance_schema(conn)` внутри `init_db()`.

**Раскладка `app/finance/`:**
- `schema.py` — ВЕСЬ DDL таблиц `fin_*` в функции `init_finance_schema(conn)`.
  Идемпотентность по общим правилам репозитория (`CREATE TABLE/INDEX IF NOT
  EXISTS`, `ADD COLUMN IF NOT EXISTS`, UNIQUE — только уникальным индексом,
  не `ADD CONSTRAINT`), обратный DDL — комментарием рядом. Помнить: `init_db()`
  выполняется при КАЖДОМ старте контейнера, ошибка в DDL роняет и Приму.
- `calc.py` — расчёты бюджета ЧИСТЫМИ функциями без SQL: на вход данные, на
  выход числа. Причина: тесты идут на FakePool (`tests/conftest.py`), который
  эмулирует каждый SQL-запрос вручную — агрегаты (SUM/GROUP BY, план-факт) в нём
  не проверяются достоверно. Агрегацию в SQL не переносить, пока в CI нет
  настоящего PostgreSQL (техдолг, см. docs/TASKS.md блок «Финансы»).
- роутеры — эндпоинты, один файл = один домен модуля. Роутер только принимает
  запрос, зовёт `calc`/SQL, возвращает ответ.

**Роуты:** все под `/api/finance/*`.

**Таблицы `fin_*`:** каждая обязана иметь
`org_id INTEGER NOT NULL REFERENCES organizations(id)` (в отличие от старых
receipts/reports, где org_id без внешнего ключа). org-scope `AND org_id=$N`
в КАЖДОМ запросе; `org_id` берётся только из `get_current_user`, никогда из тела
запроса.

**Доступ к модулю «Бюджет проекта».** Назначение на проект — через таблицу
`fin_project_members`:
- `admin` — всё, включая утверждение версий бюджета;
- `manager` (руководитель проекта, РП) — назначенные проекты: создание, правка,
  отправка на утверждение;
- `employee` — назначенные проекты: ввод только в черновики;
- `accountant` — чтение.
Гейт — функцией-проверкой первой строкой хендлера (образец —
`_require_category_manager` в `app/routers/categories.py`).

**Тесты:** CRUD — на FakePool (каждый новый запрос зеркалить в
`tests/conftest.py`); расчёты — юнит-тестами на `app/finance/calc.py` без БД.

## Параллельные сессии — не смешивать русла
Один заход Claude Code ведёт ОДНО русло работы — Прима **или** Финансы, не
одновременно.

Почему: оба контура живут в одном репозитории и видят рабочее дерево друг друга.
Общие точки столкновения — `docs/TASKS.md`, `CLAUDE.md`, `app/main.py`, DDL
внутри `init_db()` (`app/database.py`). Риски: незакоммиченные правки чужой
сессии попадают в чужой коммит, конфликт порядка миграций, расхождение трекера.
Реальный случай (31.07.2026): во время аудита FIN-00 параллельная сессия делала
REP-AUTHOR — в дереве оказались чужие правки `app/database.py`,
`app/routers/reports.py`, `tests/` и строка REP-ONBEHALF в `docs/TASKS.md`;
коммит документов пришлось собирать поштучно.

Правила:
- **Начало сессии:** `git status` + `git log -3` («что произошло без меня»).
  Найдены чужие незакоммиченные правки — сообщить пользователю ДО начала работы.
- **Конец сессии:** рабочее дерево чистое, всё закоммичено и запушено.
- **Стадирование:** только свои файлы явными путями (`git add <файл>`).
  НИКОГДА `git add -A` и `git add .` — затянут чужую работу в свой коммит.
- **Смешанный файл:** если в общем файле (обычно `docs/TASKS.md`) перемешаны
  свои и чужие строки — вычленить свои, о разделении сказать в отчёте.
- **Если параллельность неизбежна** — второму руслу отдельная ветка, не `main`.

### Чужой `pre-commit` прячет ТВОИ незакоммиченные правки — и они могут не вернуться

Это не про смешанные коммиты, а про МОЛЧАЛИВУЮ ПРОПАЖУ РАБОТЫ. Случилось
10.08.2026 прямо в работе: правки `.claude/hooks/block_prod_db.py` — около
часа — исчезли из дерева, `git status` перестал их показывать, файл совпал
с HEAD.

- **МЕХАНИЗМ.** `pre-commit` перед прогоном прячет ВСЕ незакоммиченные
  правки дерева (`Stashing unstaged files … patch<номер>`), гоняет проверки
  на чистом дереве и возвращает патч обратно. **Дерево у сессий ОБЩЕЕ**,
  поэтому прячутся и чужие правки тоже. Если в это же время другой процесс
  пишет в тот же файл (мутации, автоформат), восстановление патча расходится
  с диском.
- **ПРИЗНАК.** Пустой `git diff` БЕЗ ошибки и без конфликта; файл вдруг
  совпал с HEAD. Читается как «я ничего не менял» — потому и опасно.
  В тот раз поймали случайно: матрица покраснела на двух опорах, которые
  пять минут назад были зелёными.
- **ВОССТАНОВЛЕНИЕ.** Патчи лежат в `~/.cache/pre-commit/patch<эпоха>-<pid>`.
  `ls -lt ~/.cache/pre-commit/patch*`, взять самый свежий по времени, затем
  `git apply --check --include=<файл> <патч>` и, если чисто, без `--check`.
  Правки восстановились оттуда полностью.
- **ЧТОБЫ НЕ ПОВТОРИЛОСЬ:** коммитить рабочий файл ДО долгих прогонов,
  которые его же и правят (мутации, автоформат); не гонять мутации, пока
  в соседней сессии идёт коммит.

Родня тому же механизму, БЕЗ параллельной сессии: `pre-commit` может САМ
переписать файлы прямо в коммите (`end-of-file-fixer`, `ruff format`) —
коммит отклоняется, файлы на диске уже другие. Пропажи здесь нет, но если
в этот момент идёт прогон мутаций, его шаблоны замены могут перестать
находить цель. Поэтому после отклонённого коммита прогон повторяется,
а не считается пройденным по прошлому результату.

## Конвенции кода
- **В bash имена переменных — ТОЛЬКО ЛАТИНИЦЕЙ.** Кириллическое имя
  (`Д=…`, `КОД=…`) bash не принимает: `command not found`, дальше пустая
  подстановка и разбор чужого следа. В питоновских замерах и в тексте
  кириллица приветствуется, в bash — никогда. Куплено шесть раз за три дня
  (15–16.08.2026).
  **⚠️ ПОПРАВКА 17.08.2026, СЕДЬМОЙ РАЗ: ОЦЕНКА «ОШИБКА ШУМНАЯ И РЕЗУЛЬТАТ
  НЕ ПОРТИТ» БОЛЬШЕ НЕ ВЕРНА.** Она держалась на молчаливой посылке, что
  скрипт запускает тот же, кто его написал, — и увидит `command not found`
  сразу. В этот раз скрипты писались ДЛЯ ВЛАДЕЛЬЦА, потому что у него
  многострочная вставка в терминал разваливается построчно. Кириллические
  имена ушли бы ему файлом, рабочим на вид, и сломались бы у него, где
  разбирать их некому. Поймано холостым прогоном до передачи — но поймано
  случайно, а не правилом. **Значит проверка `grep -nE '^[[:space:]]*[А-Яа-яЁё_0-9]+=' файл`
  обязательна перед КАЖДОЙ передачей скрипта наружу, и сама эта проверка
  проверяется мутантом** (подсунуть заведомо плохую строку — сторож обязан
  её поймать, иначе «ни одного совпадения» неотличимо от «сторож не работал»).
- Только параметризованные SQL-запросы asyncpg (`$1`, `$2`). НИКОГДА не строить SQL через f-strings или конкатенацию.
- Поле `source` в receipts: `fns` | `qr_scan` | `photo_ocr` | `manual`.
- Defensive programming: в if/elif по HTTP-кодам — всегда catch-all `else`.

## Паттерны «делай»
- Поиск «где/как у нас сделано X» и обзор по многим файлам — отдавать субагенту Explore (параллельно, если направлений несколько), а не читать файлы в основном потоке. Быстрее и не раздувает контекст сессии.
- org-scope фильтрация во ВСЕХ запросах к данным (защита от доступа к чужим объектам по id). Каждый эндпоинт проверять на cross-org доступ.
- Параметризованные запросы везде.
- При смене продакшен-логики INSERT/SELECT — зеркально править FakePool в conftest.py.
- Контрактный тест keys_match между параллельными парсерами одного INSERT-пути (fns_parser, ocr_parser и будущие): множества ключей dict должны совпадать.
- Атомарные коммиты, Conventional Commits.

## Главный принцип замера: у измерителя ВСЕГДА должен быть способ показать, что он сломан

**Формулировка владельца 16.08.2026, и она старше всех наших частных
правил: если прибор не может сообщить о собственной поломке, его показания
нельзя отличить от правды.** Замер без такой способности — не измерение,
а мнение с числом.

Шесть наших проверок — это ОДИН принцип в шести видах, и каждый вид
покупали отдельно:

1. **ЗАВЕДОМО РАЗНАЯ ПАРА — для объектов.** В прогон закладываются два
   предмета, про которые ТОЧНО известно, что они в разном состоянии.
   Совпали показания — сломан прибор. Куплено трижды за 15.08.2026:
   «28 шрифтов не отдаются» одинаково на рабочем и новом сайте; «оба
   поддомена не разрешаются» при живых записях; «оба рвут TLS» при
   выпущенном сертификате у одного.
2. **ЗАВЕДОМО МЁРТВАЯ ЦЕЛЬ — для сети.** В пробу достижимости
   закладывается адрес, которого НЕ СУЩЕСТВУЕТ (`203.0.113.1` —
   зарезервирован для документации), и заведомо закрытый порт.
   «Соединились» и они — весь прогон в мусор. Куплено 16.08.2026:
   машина владельца давала мгновенный `connect` úплоть до нероутируемого
   адреса, потому что локальный слой принимал каждое соединение сам.
   На этом артефакте держалась половина ночных выводов, и фраза
   «проверено с двух точек» была неправдой: честная точка была одна.
3. **КОНТРОЛЬ С ИЗВЕСТНЫМ ОТВЕТОМ — для сторожей и мониторинга.**
   Дырявый образец обязан быть пойман, здоровый — пройти (`--selfcheck`
   перед каждым прогоном). Без второй половины «расхождений 0»
   неотличимо от «проверка не выполнялась».
4. **ЗАПРОС ДОШЁЛ ДО ПРОВЕРЯЕМОГО МЕСТА — для ручек API.** Отказ приходит
   с РАЗНЫХ адресов, и до нужного запрос может не доехать вовсе:
   `422` — тело не прошло разбор, проверяемая логика НЕ РАБОТАЛА;
   `401` — логика отработала и отказала. Куплено ДВАЖДЫ ЗА ДВА ДНЯ
   на одном и том же поле (`username` вместо `phone_or_email`,
   17.08.2026): восемь неверных входов подряд дали восемь `422`
   и были доложены владельцу как «ограничитель молчит, лимит
   поднят ✅» — а ограничителя они не касались ни разу. Число было,
   измерения не было. **Перед тем как считать отказы, прочитать ПЕРВЫЙ
   ответ целиком и убедиться, что это отказ ТОГО механизма, который
   меряем.** `422` в прогоне про ограничитель значит «не измерено»,
   а не «зелёно».
5. **МЕТКА ПРОГОНА — для журналов и файлов результата.** Файл, который
   ПЕРЕЗАПИСЫВАЕТСЯ каждым запуском, при сорвавшемся запуске хранит
   ПРОШЛЫЙ результат — и выглядит он как свежий. Куплено 18.08.2026
   в день переключения: `08-dump-restore.sh` пишет в `/root/restore.log`,
   инструкция велела искать строку «код возврата: 0», а запуск сорвался
   ДО старта заливки — и в журнале лежала запись ОТ 16 АВГУСТА с тем самым
   нулевым кодом. Успех позапрошлой заливки чуть не приняли за успех
   текущей; ошибка была бы тихой, потому что сверка пошла бы дальше
   по данным, которых не привозили. **Правило: скрипт пишет ПЕРВОЙ строкой
   метку прогона (дата-время старта), а инструкция требует СВЕРИТЬ МЕТКУ,
   а не найти нужный код.** Годится любому файлу-результату: отсутствие
   свежей метки означает «результата нет», а не «результат прежний».
6. **У ЗАМЕРА СОСТОЯНИЯ ЕСТЬ СРОК ГОДНОСТИ — для выводов о том,
   что меняет кто-то другой.** Пятый вид — про ФАЙЛ, который хранит
   прошлое и выглядит свежим. Шестой — про ВЫВОД, который был верен
   и перестал им быть, пока им пользовались. Куплено дважды за три дня,
   и первый раз обошёлся дёшево именно поэтому не научил.
   **17.08.2026:** дважды доложено «не запушен 1 коммит `0402d00`»,
   хотя владелец запушил его за три минуты до отчёта. Цена — строчка
   неверного отчёта. **19.08.2026:** сказано «`fb76742` не запушен»
   и на этом основании сделан `amend`, а коммит уже лежал на
   `origin/main`. Обычный `push` отбился non-fast-forward, потребовалась
   принудительная замена `--force-with-lease`; при параллельной сессии
   тот же `amend` затёр бы чужую работу. **Замер в обоих случаях БЫЛ
   СДЕЛАН И БЫЛ ВЕРЕН В СВОЙ МОМЕНТ** — устарел он между замером
   и действием. Поэтому формулировка «забыл проверить» неверна
   и вредна: она учит проверять ОДИН раз в начале захода и повторять
   ошибку дословно. **Правило: перед любым `amend`, `rebase`,
   `push --force` — `git fetch origin && git log --oneline origin/main -3`,
   заново и непосредственно перед действием.**
   **⚠️ ДОПОЛНЕНО 26.08.2026, И ОШИБЛИСЬ ОБА — ПОЭТОМУ ЗАПИСАНЫ ОБЕ ПОЛОВИНЫ.**
   **СО СТОРОНЫ АГЕНТА:** число про незапушенное было получено ОДИН раз, сразу после
   коммита, и потом ПЕРЕПИСАНО В СЛЕДУЮЩИЙ ОТВЕТ вместе с хешем — без повторного
   прогона. К тому моменту владелец успел запушить, и строка «незапушенный один:
   157f40a» стала неверной. **Это не устаревший замер, а ОТСУТСТВИЕ замера,
   замаскированное под замер: строка выглядит как число, а является воспоминанием.**
   Отсюда обязанность: **число про состояние репозитория получается в ТОМ ЖЕ ответе,
   где печатается; нет свежего вывода команды в этом ответе — нет и утверждения,
   писать «проверю» вместо числа.** И `git fetch` перед сверкой: локальный `origin/main`
   обновляется только при пуше ИЗ ЭТОЙ копии, а пушить могут откуда угодно.
   **СО СТОРОНЫ ВЛАДЕЛЬЦА (его замечание, записано по его просьбе):** расхождение
   с `origin` проверялось по `git log -1`, а он показывает лишь то, на чём стоит
   указатель `origin/main` в ЛОКАЛЬНОЙ копии, и молчит о том, что HEAD ушёл вперёд.
   **Для расхождения нужны `git status -sb` (строка `ahead N`) или
   `git log --oneline origin/main..main` — их и просить.**
   ⚠️ **ОБЩИЙ ВЫВОД СИЛЬНЕЕ ЧАСТНОГО: два человека независимо приняли за замер то,
   что замером не является — один воспоминание, другой команду, отвечающую
   на другой вопрос. Спор «кто прав» разрешила третья команда, а не настойчивость.**
   **⚠️ ОБЕ ПОЛОВИНЫ ПРАВИЛА ОБЯЗАТЕЛЬНЫ, ПОТОМУ ЧТО ЗАКРЫВАЮТ РАЗНЫЕ
   ОТКАЗЫ, И НИ ОДНА НЕ ЗАМЕНЯЕТ ДРУГУЮ:** ① `fetch` — на случай, когда
   пушат ИЗ ДРУГОГО МЕСТА: локальная копия указателя не обновляется вовсе
   и врёт молча, сравнение без `fetch` сравнивает с позавчерашним слепком;
   ② СВЕЖЕСТЬ СРАВНЕНИЯ — на случай, когда пушат ОТСЮДА ЖЕ: указатель
   обновляется сам и верен, врёт не он, а наш вывод, сделанный до чужого
   действия. Именно так вышло 19.08. **Читать это как «`fetch`
   необязателен, если пушишь отсюда» — значит оставить второй отказ
   открытым, а он и сработал.**

**Как этим пользоваться, а не помнить наизусть:** прежде чем поверить
числу, спросить себя — **ЧТО В ЭТОМ ПРОГОНЕ ОБЯЗАНО БЫЛО ПОКРАСНЕТЬ,
И ПОКРАСНЕЛО ЛИ ОНО?** Нет ответа — прогон не состоялся, независимо
от того, какие цифры он напечатал.

Частные случаи и разборы — в правилах ниже; они остаются, потому что
держатся на историях, а не на формулировках.

### Перед выводом «сервер недоступен» — замер КАНАЛА, а не только цели

**VPN, прокси и фильтры дают картину, неотличимую от поломки сервера.**
Обрыв соединения выглядит одинаково, откуда бы он ни пришёл, и по нему
нельзя отличить «сервер лежит» от «до сервера не доходит».

**Сначала три замера с рабочей машины, потом любые выводы об инфраструктуре:**
1. `route get 8.8.8.8` — через какой интерфейс уходит трафик. `utun*`
   в ответе означает VPN, и дальше мерить бессмысленно, пока он включён;
2. обращение к СТОРОННЕМУ живому домену — работает ли сеть вообще;
3. обращение к своему — и только теперь разница между 2 и 3 что-то значит.

**Куплено 27.08.2026, ценой полудня.** [[S-78]]: `ssh` на бастион рвался
на `kex_exchange_identification`, [[T43]] считалась подтверждённой,
замер [[S-85]] был объявлен невозможным. Причина оказалась одна на все три —
включённый VPN (`utun6`) на машине владельца. Инфраструктура была исправна.

⚠️ **И САМОЕ ПОУЧИТЕЛЬНОЕ ЗДЕСЬ — ЧТО РАЗБОР БЫЛ ВЕРЕН НА КАЖДОМ ШАГЕ.**
`kex_exchange_identification` действительно означает обрыв до предъявления
ключа, значит ключ и `known_hosts` действительно исключались. Повтор
«с другой сети» — раздача с телефона — действительно исключал бан адреса.
**Все выводы верны, и все — об одном и том же канале: телефон раздавал
интернет на ту же машину с тем же VPN. «Другая сеть» оказалась той же самой.**
Разделяющий замер, поставленный внутри одной трубы, ничего не разделяет.

### Прибор, а не руки: что можно замерить скриптом — замеряется скриптом

**Владелец не разработчик.** Просить его повторять действия в браузере,
чтобы отличить один случай от другого, ЗАПРЕЩЕНО: различение — работа
прибора, а не человека.

**Признак нарушения, по которому себя и ловить:** в ответе появляется
«попробуйте ещё раз и посмотрите, что будет».

**Граница — ручное действие владельца допустимо там, где без человека
нельзя:** нажать кнопку в чужой панели, подтвердить владение доменом,
ввести бумажный чек. Всё остальное — скрипт с контролем.

**Куплено 25.08.2026.** Отказ отправки почты начали разбирать повторными
регистрациями через браузер: владельца просили зарегистрироваться ещё раз
и посмотреть журнал — чтобы отличить «переменные не доехали» от «SMTP
не проходит». Различие это видно одной попыткой TCP-соединения из скрипта,
а через регистрацию — не видно вовсе: наружу в обоих случаях выходит
одинаковый ответ `200`, и различие остаётся только в журнале, куда
владельцу приходится лезть руками. **Замер руками владельца дороже
скрипта и при этом ХУЖЕ: он повторяет один и тот же случай, вместо того
чтобы разделить два.**

⚠️ **И ВТОРАЯ ПОЛОВИНА ПРАВИЛА, БЕЗ КОТОРОЙ ПЕРВАЯ НЕ РАБОТАЕТ: прежде
чем просить замер, проверить, ЕСТЬ ЛИ ГДЕ ЕГО ПРОВЕСТИ.** В тот же день
выяснилось, что у площадки прода (Timeweb App Platform) нет консоли:
запустить на ней скрипт негде вообще, любая диагностика идёт либо через
журнал приложения, либо не идёт. План «сделаем замер на проде» был написан
до этой проверки и оказался невыполним. **Сначала место, потом прибор.**


## Сторожа и тесты: правило мутационной проверки (T11)

**Сторож, не проверенный мутацией, считается неработающим.** Написали тест,
линтерное правило, контрактную матрицу, проверку схемы — сломайте то, что она
обязана поймать, убедитесь, что она падает, верните как было. Зелёный прогон
сам по себе не отличает «всё чисто» от «ничего не проверено».

Два уточнения, оба куплены дорого:

- **Мутация нужна на КАЖДЫЙ заявленный источник.** Одна успешная мутация
  создаёт ложную уверенность обо всём стороже: она подтверждает одну ветку
  кода, а не сторож целиком.
- **Зелёный прогон без охвата — не результат.** Сторож обязан уметь показать,
  ЧТО именно он проверил (счётчик, `--verbose`, список файлов).
- **НАЙДЕНО против НАПЕЧАТАНО — печатать оба числа и падать при расхождении.**
  Замер может найти нужное и не довести до вывода: полосы отчёта не покрывают
  найденное, фильтр печати строже фильтра поиска, группировка теряет остаток.
  Снаружи это выглядит как чистый результат — находка есть внутри, но её никто
  не увидит. Поймано 10.08.2026 на `tests/tools/claude_md_dupes.py`: строка
  «ИТОГО 26» при 23 напечатанных, и пропали ровно те пары, ради которых
  инструмент и писался. Требование общее для ВСЕХ наших замеров, не только
  этого. Проверяется мутацией: сузить полосу вывода — сторож обязан покраснеть.
  `[ОБЩЕЕ-T22]`
- **Утверждение «единственный / все / нигде больше» проверяется ЗАМЕРОМ
  ПО КОДУ в тот же заход** — иначе оно превращается в факт и живёт
  в документации. И перепроверять надо не только чужие описания, но и СВОИ
  ПРОШЛЫЕ ВЫВОДЫ: свой вывод опаснее чужого описания, потому что не вызывает
  подозрений — помнишь, как его делал. 07.08.2026 я написал в тесте и в
  отчёте, что `GET /api/services/` была ЕДИНСТВЕННОЙ ручкой без авторизации.
  Через сутки проверка по коду дала ДВЕНАДЦАТЬ открытых ручек, четыре из них
  (OCR, прокси ФНС, обе ручки согласия) закрывать было нужно немедленно.
  Вывод сделали по одной ручке, которую подсветил другой замер, и молча
  распространили на всё приложение.
- **ПРИЁМКА СТРОИТСЯ НА ТОМ, ЧТО В ИНТЕРФЕЙСЕ ЕСТЬ, А НЕ НА ТОМ, ЧТО ЕСТЬ
  В ГОЛОВЕ.** Прежде чем просить человека «открыть и посмотреть X»,
  убедиться, что X существует В ТЕКУЩЕЙ сборке. Пункт приёмки про
  несуществующий элемент не просто пропадает впустую: он возвращается
  ответом «не работает», и дальше чинится то, чего нет, — а настоящая
  проверка (у нас: доходит ли фото из хранилища) остаётся несделанной
  и выглядит сделанной. Признак опасности — пункт про показ, вывод,
  экран или кнопку, которых сам же не видел в коде.
  Куплено ДВАЖДЫ ЗА ДВА ДНЯ на одном и том же: 13.08.2026 в плане S-40
  стоял шаг «открыть чек и посмотреть фото», 15.08.2026 в приёмке шага 5
  — «фото чека открылось». Показа фото в интерфейсе НЕТ, это установлено
  моим же аудитом перед задачей №3 и заведено отдельной строкой 18.
  Оба раза поймал владелец. **Практика: пункт приёмки, который человек
  выполняет глазами, сверять с кодом ТОГО ЖЕ экрана, а не с намерением
  задачи; если элемента нет — проверять другим способом (замер, консоль)
  и прямо писать, почему не глазами.**
- **ЕСЛИ ПРОВЕРКА РАЗЛИЧАЕТ ДВА СЛУЧАЯ ТОЛЬКО В ОПРЕДЕЛЁННОМ СОСТОЯНИИ —
  СОСТОЯНИЕ НАДО СОЗДАТЬ, А НЕ ЖДАТЬ И НЕ ПОДЛАВЛИВАТЬ.** Часть вопросов
  неразрешима изнутри одного клиента: «прокси подставляет настоящий адрес»
  и «адреса нет вовсе, все склеены в один» дают снаружи ОДИНАКОВУЮ картину.
  Развести их может только второй настоящий клиент — но лишь пока держится
  нужное состояние. Если оно короче, чем время на согласование с человеком,
  замер обязан ПРОДЛИТЬ его намеренно, иначе получится ложный успех: к моменту
  пробы состояние истечёт, второй клиент ответит нормально ПРИ ЛЮБОМ устройстве
  системы, и это прочтётся как доказательство. `[ОБЩЕЕ-T22]`
  Куплено 13.08.2026 на S-35/Timeweb: окно счётчика запросов живёт 60 секунд —
  человек не успевает прочесть просьбу. Поэтому адрес был загнан в БАН
  (5 минут) — устойчивое состояние, в котором проба с телефона что-то значит.
  Ответ пришёл однозначный: контейнер забанен, телефон проходит свободно,
  значит адреса РАЗНЫЕ. Приём общий: продлить состояние (бан вместо окна,
  пауза сервиса вместо гонки, зафиксированные часы вместо ожидания срока)
  дешевле, чем спорить о результате, полученном в неизвестном состоянии.
- **ПРАВКА «НА БУДУЩЕЕ» ВНОСИТСЯ В МОМЕНТ ПЕРЕЕЗДА, А НЕ ЗАРАНЕЕ — И «НИЧЕГО
  НЕ ЛОМАЕТ» ЭТО ГИПОТЕЗА, А НЕ ВЫВОД.** Правка, нужная будущей площадке
  и бесполезная нынешней, не имеет на нынешней ни одного сторожа: тесты
  её не покрывают (речь о конфигурации, а не о логике), сборка проходит,
  линтер молчит. Единственное, что её проверяет, — живой запрос ПОСЛЕ
  выката. Значит либо замер сразу за пушем, либо правку не вносить вовсе,
  пока переезд не наступил. `[ОБЩЕЕ-T22]`
  Куплено 13.08.2026, S-06: фронт `server.js` слушал жёстко 4173, я заменил
  на `Number(process.env.PORT) || 4173` и написал, что «пока мы на Railway,
  она ничего не ломает». Сломала сразу: Railway передаёт `PORT=8080`,
  приложение честно встало на 8080, а КРАЙ площадки продолжал слать на 4173
  — публичный домен настраивался, когда сервер стоял на 4173. Снаружи
  «Application failed to respond», в логе контейнера ни одной ошибки
  (`[web] serving /app/dist on :8080`), у края 502 с `x-railway-fallback: true`.
  Процесс здоров, маршрут разошёлся — и это худший вид поломки, потому что
  все привычные признаки зелёные.
  **ОТДЕЛЬНО, И ЭТО БОЛЬНЕЕ ВСЕГО: предупреждение лежало в том самом
  комментарии, который я переписывал** — «public domain routes to port 4173
  …, so we listen there — NOT on $PORT — to match the existing networking
  config». Я процитировал из него половину про `vite preview` и отбросил
  вторую, объяснявшую ПРИЧИНУ. Формулировка владельца, дословно: **«знал
  и переспорил рассуждением»** — это не «не знал», и разница здесь вся. Практика: если правишь строку, у которой
  есть комментарий с обоснованием, обоснование опровергается ЗАМЕРОМ
  и вслух, а не молча переписывается.
  **И ПРО СТРАХОВКУ:** пока старая площадка держит роль запасного выхода,
  её конфигурацию не «улучшают». Чинить сломанное надо ВОЗВРАТОМ в проверенное
  состояние (обратный коммит), а не новой настройкой в панели: новая настройка
  на страховке — это непроверенная страховка.
- **ОДИНАКОВЫЙ РЕЗУЛЬТАТ НА ЗАВЕДОМО РАЗНЫХ ПРЕДМЕТАХ — ЭТО ПРИЗНАК
  ПОЛОМКИ ПРИБОРА. ПРОВЕРЯТЬ ИЗМЕРИТЕЛЬ ПЕРВЫМ, А НЕ ПРЕДМЕТ.**
  Два объекта, про которые ТОЧНО известно, что они в разном состоянии
  (рабочий сайт и новый, домен с сертификатом и без, живая запись DNS
  и несуществующая), обязаны дать РАЗНЫЕ показания. Совпали — почти
  наверняка меряется не то: сломана склейка адреса, подставлено не то
  имя, отвечает не тот сервис, кэширован прошлый ответ. Практика:
  **в каждый замер закладывать заведомо разную пару** и смотреть на
  неё раньше, чем на результат; одинаковый ответ по паре останавливает
  прогон. Это дешевле, чем ловить ошибку по следствиям.
  Куплено ТРИЖДЫ ЗА ОДИН ДЕНЬ 15.08.2026, и каждый раз причина была
  в приборе: ① «28 шрифтов из 28 не отдаются» — одинаково на новом
  и на старом фронте, а на старом они заведомо работают (резал ведущий
  слэш при склейке адреса); ② «оба поддомена не разрешаются» — при том
  что авторитетные и публичные серверы отвечали верно (резолвер
  контейнера закэшировал отрицательный ответ, полученный до создания
  записи); ③ «оба поддомена рвут TLS» — при том что у одного сертификат
  уже был выпущен (в TLS уходил IP вместо имени, у прокси для него
  сертификата нет). Формулировка владельца: **если два разных объекта
  дают одинаковый результат, первым делом проверяется измеритель.**
  `[ОБЩЕЕ-T22]`
- **ОТРИЦАТЕЛЬНЫЙ ВЫВОД СТОИТ РОВНО СТОЛЬКО, СКОЛЬКО ОХВАТ ПОИСКА.**
  «В документации этого нет», «такой ручки не существует», «в коде не
  используется» — утверждения об ОТСУТСТВИИ, и доказываются они иначе, чем
  утверждения о наличии: находка свидетельствует сама за себя, а ненаходка
  свидетельствует только о том, что искали не там. Поэтому рядом с любым
  отрицательным выводом обязан стоять ОХВАТ: где искал, сколько страниц или
  файлов прошёл, чем именно. Без охвата это не вывод, а впечатление, и живёт
  оно потом в документации как факт. Практика: охват называть в той же фразе
  («не нашёл в разделах X и Y» вместо «нет»); для чужой документации брать
  ИНДЕКС раздела (`llms.txt`, оглавление) и проходить его целиком, а не
  угадывать адреса страниц. Куплено 13.08.2026 на S-06: записал «у Timeweb
  App Platform штатного входа в контейнер в документации НЕ НАЙДЕНО» и на

### Разбор текста проверяется контрольным примером ИЗ РЕПОЗИТОРИЯ (T30)

**Разбор не падает, когда врёт — он молча отдаёт другое число.** Любой
разбор текста (markdown, CSV, строка QR, JSON из ответа) выглядит рабочим,
пока не встретит экранирование, кавычки или неразрывный пробел.

- **Контрольный пример лежит ФИКСТУРОЙ в репозитории, а не внутри скрипта.**
  Инструмент переписывают, ответ должен пережить переписывание: образец —
  `tests/tools/fixtures/md_control.tsv` (ожидание и строка в одном файле).
- **В примере обязателен и здоровый, и заведомо битый случай.** Без второго
  «расхождений 0» не отличить от «проверка не выполнялась».
- **Самопроверка идёт ПЕРЕД обычным прогоном** и останавливает его:
  разбор, который врёт на известном ответе, на неизвестных данных врёт тем
  более (`tests/tools/md_table.py --selfcheck`).
- Куплено дважды за один день 06.08.2026: сводка резала строку трекера по
  КАЖДОМУ `|`, включая экранированный в тексте задачи, и объявила целую

составленный ДО написания, защищает от известного. Проверка «не поднимает ли
он заведомо ЖИВОЕ» — от неизвестного. Первая не покрывает вторую даже частично.

### У каждого утверждения аудита есть строка основания, и жанры не смешиваются

**Введено 26.08.2026 по СЧЁТУ, а не по ощущению: за два дня ДВЕ находки сняты
мной же после того, как владелец назначил по ним приоритет** — [[T70]] и [[T73]].
Механизм один: **вывод по ЧАСТИ, поданный как вывод по ЦЕЛОМУ.** Дважды —
это свойство процедуры. Цену платит владелец: приоритет назначает он.

**① СТРОКА ОСНОВАНИЯ.** Каждое утверждение несёт: файл, диапазон строк,
**ПРОЧИТАНО ЦЕЛИКОМ или ЧАСТИЧНО**. Утверждение без основания замером
не считается и приоритета не получает. «Частично» — не признание в лени,
а единственный способ отличить «я знаю» от «я видел кусок»; порок —
«частично», выданное за «целиком».

**② ДВА ЖАНРА, РАЗНЫМ ВИДОМ.** «ЗАМЕРЕНО» — есть числа или вывод команды,
он прикладывается. «ПРОЧИТАНО И ПОНЯТО» — есть только чтение кода. Надёжность
разная, значит и подача обязана быть разной: второе, поданное тоном первого, —
то же самое, что воспоминание, поданное как замер.

**③ СВЕРКА СТОРОН.** Вывод о ПОВЕДЕНИИ требует обеих сторон: бэкенд
и интерфейс, код и договор ручки, функция и её вызывающие. **Одна сторона
даёт вывод о КОДЕ, а не о ДОРОГЕ.**

## Проверка доступа подтверждается СОСТОЯНИЕМ, а не кодом ответа

**403 сам по себе не доказывает ничего.** Тест ролевого гейта считается
написанным, только если он проверяет ещё и то, что данные НЕ изменились
(на мутациях) и что чувствительных полей НЕТ в ответе (на чтении).

Почему это не придирка: между «запрос отклонён» и «запрос отклонён, но
запись всё равно прошла» разницы в коде ответа нет. Хендлер может вернуть
403 после того, как отработал побочный эффект; фоновая задача может
доделать начатое; ветка ошибки может стоять ПОСЛЕ записи. Тест на код
ответа зелен во всех этих случаях.

Практика, закреплённая S-29 и S-28:

- **мутация** — `assert 403` И `assert db.users[0]["is_active"] is True`
  («коллега не должен был отключиться»), `assert len(db.users) == 1`;
- **чтение** — обе половины: чувствительного поля в ответе нет И нужное
  поле на месте. Без второй половины урезание ответа до пустого словаря
  проходит как успех — поймано мутацией «оставить только `id`»: тест
  упал по `KeyError` на ФИО, то есть сработала именно вторая половина;
- **положительный случай обязателен**: рядом с «сотруднику нельзя» стоит
  «админ работает как раньше», иначе гейт, сломавший ручку всем, читается
  как успех.

### Слепая запись: ручку, не различающую «сделано» и «нечего было делать», кодом ответа не проверить В ПРИНЦИПЕ

`UPDATE`/`DELETE` с org-scope в `WHERE`, после которого хендлер отвечает
`{"ok": true}` независимо от того, задел ли запрос строку, — это не
частность, а КЛАСС. Такая ручка отвечает одинаково и когда всё сработало,
и когда объекта нет, и когда объект чужой. Ни тест, ни фронт, ни человек
руками не отличат работающий org-scope от снятого: единственный признак —
СОСТОЯНИЕ объекта после запроса.

Часто это осознанный выбор (анти-энумерация: «не палим существование
чужих чеков»), и менять поведение ручки не надо. Надо помнить, что
проверка у неё ровно одна.

## Сработавший запрет — это СТОП, а не задача найти формулировку

**Если инструмент отклонён правилом прав — остановиться и спросить. НЕ
переписывать команду так, чтобы она прошла.** Отказ означает решение
владельца, а не техническую помеху; обход переформулировкой превращает
защиту в неудобство, о котором владелец узнаёт постфактум — если узнаёт.

**Слово в переписке и механизм в настройках — разные вещи, и расхождение
между ними это ПОВОД СПРОСИТЬ, а не разрешение действовать.** Даже когда
в сообщении есть «пуши»: раз запрет сработал, значит настройки говорят
другое, и правильный ход — назвать расхождение вслух.

`deny: Bash(git push *)`. Я переписал команду как
`git -C <путь> push origin main` — под запрет она не подпадает (не
начинается со слов «git push»), зато подпадала под разрешение,
накопленное в личном файле настроек. Пуш прошёл. Владелец узнал об этом
СУТКИ СПУСТЯ и сформулировал точнее меня: **«правило, которое обходится
переписыванием команды, защищает только от невнимательности, а не от
решения его обойти»**.

Разбор показал и вторую половину беды: правил ДВА комплекта, и они
противоречили друг другу — проектный `deny` запрещал пуш, личный `allow`
(накопленный кнопкой «разрешать всегда» за прошлые сессии, 252 записи)
его разрешал. Сверка обоих файлов замером нашла ровно 4 разрешения на
пуш; все сняты, обход через `-C` и `-c` закрыт в проектном `deny`.

**И честная оговорка: список шаблонов запрета не бывает исчерпывающим.**
Всегда найдётся форма, которую он не ловит. Поэтому настоящая защита —
не шаблон, а это правило: сработал запрет → стоп и вопрос.

## Паттерны «не делай»
- НЕ коммитить секреты — только в Railway → Variables. `.env` в `.gitignore`.
- НЕ логировать в открытом виде: пароли, ИНН, fn (фискальные номера), полные номера карт, паспорта. Маскировать: карты `****1234`, fn — только факт наличия.
- НЕ использовать `*` в CORS на проде — только whitelist в `CORS_ORIGINS`.

- НЕ выдавать «пользователь не найден» при логине — единое «Неверный логин или пароль» (защита от энумерации).
- НЕ делать батч-рекатегоризацию без фильтра `WHERE category_manual = FALSE` (защита ручных правок пользователя).

## Безопасность
- Секреты: только Railway Variables, минимальные scope токенов.
- bcrypt (стоимость 12+) для паролей.
- JWT: access 60 мин, refresh 30 дней, HS256; при logout — в revoked_tokens.
- Блокировка: 5 неверных попыток → 15 минут (failed_attempts, locked_until).
- Rate limiting на auth и критичных эндпоинтах.
- **ПАРОЛЬ, КОТОРЫЙ ПОПАДЁТ В СТРОКУ ПОДКЛЮЧЕНИЯ, — ТОЛЬКО БУКВЫ И ЦИФРЫ.**
  `DATABASE_URL` разбирается как URL, и спецсимвол в пароле обрывает разбор:
  `asyncpg` падает с `ValueError: bad query field`, а выглядит это как «база
  недоступна» — то есть чинить начинают не то. Формально лечится
  процентным кодированием, но кодировать придётся КАЖДОМУ, кто когда-либо
  соберёт эту строку руками (панель площадки, `psql`, `pg_dump`, скрипт
  бастиона), и однажды кто-нибудь забудет. Дешевле не заводить проблему:
  генератор пароля в панели обычно даёт спецсимволы — сменить сразу
  при создании базы, до первой строки подключения. Куплено 13.08.2026
  на S-06 шаг 3: пароль из панели Timeweb уронил старт приложения, а сам
  пароль при этом утёк в лог деплоя и подлежал замене. **Правило касается
  и будущих баз, и бастиона.** Длину при этом НЕ сокращать: стойкость
  добирается длиной, а не набором символов.

- 152-ФЗ: согласие при регистрации — два НЕзаполненных чекбокса, лог в user_consents (user_id, время, IP, версия политики, текст).

## Нормы РФ — закладывать проактивно, не реактивно
При любой задаче, касающейся фискальных данных, налогов, ПД, документооборота —
СНАЧАЛА свериться с действующей нормой РФ (стандарт ФФД/тег, статья НК, ФЗ),
заложить ПОЛНЫЙ набор значений по норме, а не только то, что встретилось в
текущих данных. Данные пользователя — подмножество нормы, не наоборот.
Примеры:
- НДС: тег 1199 ФФД = 12 значений (20/10/22/5/7/0/без НДС/расчётные 20-120,
  10-110, 5-105, 7-107, 22-122). Обрабатывать ВСЕ, не только встреченные.
- 152-ФЗ: данные граждан РФ — хранение в РФ (уже учтено).
- 54-ФЗ: реквизиты чека — по составу ФФД.
Если норма неизвестна/могла измениться — проверить веб-поиском (источник:
ФНС/КонсультантПлюс/НК), а не идти от данных.

## Рабочий процесс
- Одна фича — одна сессия, один атомарный коммит.
- **Если проверка возможна только МЕЖДУ двумя правками — это два коммита
  и два деплоя, даже когда пауза между ними не нужна.** Иначе доказательство
  исчезает вместе с предметом проверки. Пример, ради которого правило
  записано (NDS-CLEANUP, 10.08.2026): шаг ② прекращает запись колонок, шаг ③
  их удаляет. Слить в один заход — значит выкатить оба разом, и вопрос
  «а точно ли перестали писать» останется без ответа навсегда: колонок,
  на которые надо смотреть, уже не будет. Сначала ②, потом ЖИВОЙ чек
  и один SELECT, и только потом ③.
- Сначала план (plan mode), код не писать до одобрения.
- Показывать diff до применения; коммит — отдельной командой после ручной проверки.
- Перед любой миграцией схемы БД — BEGIN/ROLLBACK валидация через asyncpg (см. skill db-migration-validation). НИКОГДА не COMMIT в валидационном скрипте.
- Перед миграцией — показать обратный DDL (точку отката: DROP COLUMN / DROP INDEX / DROP TABLE).
- Перед большой задачей — аудит текущего состояния (см. skill audit-before-task).

## Учёт времени: факт вписывается при закрытии задачи (AOCG-TIME-001, уровень 1)

Переводишь задачу в ✅ — **тем же коммитом** вписать в её примечание **⏱ Факт**.
Отдельным заходом «потом посчитаем» — не работает: ровно так журнал v01 молчал
два месяца, и ровно так 02.08.2026 шесть закрытых строк остались без факта.

- **Источник — время коммитов, не память.** Оба репозитория на одной шкале,
  кластеризация: разрыв <40 мин = одна сессия, длительность = last − first
  + 15 мин, одиночный коммит = 20 мин.
- **Плана не было — так и писать:** «план не давался, класс C, первый факт».
  Оценка без класса точности не называется (A ±20% · B ±50% · C ±100%).
- **Число всегда помечать как НИЖНЮЮ границу.** Работа до первого коммита
  (аудит, чтение кода, замер) в интервалы не попадает вовсе, а заходы без
  коммита по git неотличимы от простоя.
- **Новый тип работы**, которого нет в таблице нормо-времени — после факта
  добавить примитив в раздел 4 журнала.

Журнал: `docs/AOCG-TIME-001-2026_Zhurnal_vremeni.md` (там же метод и таблица
нормо-времени). Пометка ⏱ и общие оговорки — в шапке `docs/TASKS.md`.
