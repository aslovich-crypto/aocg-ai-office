# Защита Claude Code от опасных операций

Два слоя, чтобы Claude Code не мог по ошибке тронуть секреты, прод-БД
или запушить без твоего ведома.

## Слой 1 — deny-список (`.claude/settings.json`)

Блокирует по шаблону: чтение секретов (.env, .ssh, ключи), деструктив
(rm -rf, git reset --hard, git push, sudo), опасные команды площадки.
Откат несохранённых правок (git checkout/restore) — спрашивает каждый раз.

**Шаблонов «SQL по подстроке» здесь БОЛЬШЕ НЕТ (07.08.2026, S-39.)**
Раньше стояли `*DROP TABLE*`, `*DROP INDEX*`, `*DROP DATABASE*`,
`*DELETE FROM*`, `*TRUNCATE*`, `dropdb*` — шесть правил, ловивших подстроку
в ЛЮБОЙ команде. Они останавливали не только запросы к базе, но и рассказы
о них: `echo`, сообщение коммита, поиск по репозиторию. Два слоя с разной
логикой — это не двойная защита, а два источника ложных срабатываний
и невозможность понять, кто сработал. Теперь про SQL отвечает только хук,
и он умеет назвать, ЧТО именно увидел.

## Слой 2 — хук (`block-prod-db.sh` → `block_prod_db.py`, PreToolUse на Bash)

Блокирует ИСПОЛНЕНИЕ деструктивного SQL против боевой базы. Решает не по
подстрокам, а по разбору: что реально исполнится (голова команды, с учётом
кавычек) и куда оно подключится (адрес из строки подключения; спрятанный
адрес трактуется как боевой). Нагрузку ищет там, куда её передали — `-c`,
`-f`, heredoc, `$(…)`, файл-аргумент любого расширения.

- Локальную базу не трогает (адрес явно localhost).
- Чтение боевой базы не запрещает — запрещает запись.
- Инструменты кода (`pytest`, `ruff`, `black`, `mypy`, `isort`, `flake8`,
  `pip`) пропускает всегда: они ходят по файлам, а не по базе, но файлы
  бывают полны SQL как данных.
- При невозможности разобрать команду — ПРОПУСКАЕТ и пишет предупреждение.
  Сторож, падающий в «запрещено всё», снимают в тот же день.

- Комментарии в файлах не считаются деструктивом: по регламенту обратный
  DDL пишется комментарием рядом с миграцией, и сторож блокировал
  правильно оформленную миграцию (T5). Снимаются они токенизатором для
  `.py` и разбором кавычек для `.sql` — наивная регулярка «от `#` до конца
  строки» срезала бы и запрос, стоящий за решёткой ВНУТРИ строки.
  С самой команды комментарии не снимаются: там сторож остаётся строгим.

**Спецификация — не код, а матрица форм `tests/tools/hook_probe.py`.**
Меняешь поведение — сначала строка в матрице, потом правка хука. Точный
счёт случаев печатает сам прогон; здесь он не дублируется намеренно —
число в документе устаревает первым и молча.

```bash
./venv/bin/python tests/tools/hook_probe.py             # вся матрица
./venv/bin/python tests/tools/hook_probe.py --selfcheck  # только самопроверка
./venv/bin/python tests/tools/hook_mutations.py          # ломает и проверяет
```

**Матрица без мутаций — список, а не проверка.** `hook_mutations.py` по
очереди ломает каждую заявленную способность хука и требует, чтобы
покраснели ровно те случаи, которые за неё отвечают; файл хука
восстанавливается в любом исходе.

Самопроверка идёт ПЕРЕД каждым прогоном и проверяет сам замер: отвечает ли
хук, не запрещает ли он всё подряд, целы ли данные матрицы. Без неё замер
дважды показывал ровную таблицу, не проверив ничего (T26, случаи 12 и 13).

## Когда временно снимать защиту

Push и миграции схемы БД заблокированы намеренно — это осознанные операции.

**Деплой:** push делаешь вручную. Либо на время закомментируй правило
`git push` в settings.json и верни после.

**Миграция БД** (DROP/CREATE индекса и т.п.):

1. Отключи хук (`/hooks` или правка `.claude/settings.json`).
2. Прогони BEGIN/ROLLBACK-валидацию, затем применение.
   ⚠️ Хук блокирует и саму валидацию — он не отличает ROLLBACK от COMMIT
   по тексту. Поэтому защиту снимаешь на весь цикл «валидация → применение».
3. Сразу верни защиту обратно и прогони матрицу.

## Управление

- Посмотреть/переключить правила и хук: меню `/hooks` или правка
  `.claude/settings.json`.
- Если хук не подхватился — открой `/hooks` один раз (перечитает конфиг).
